SHERPA · 2026-09-20 · Basic controls · States

Control states: idle · hover · pressed · disabled · focus

One rule applies everywhere: hover changes only the surface. The background appears or moves one shade along the scale. Text and borders stay the same. Pressing moves another shade along the same scale. Surface scale: transparent → 1b1e24 → 22252b → 2b2f36 (filled buttons have their own 3-shade scale). Text colour cannot do this because, after the 09-12 contrast pass, the tokens 8a8f98 … e0e2e7 all resolve to the same white in the dark theme and the same black in the light theme. A "one shade brighter" hover is invisible. Links are the only exception. They have no surface, so hover and pressed states follow the accent scale (the contrast pass kept the accent tokens distinct), with no underline. Disabled: opacity .45, default cursor, no hover. Focus applies only with keyboard navigation (:focus-visible), with a 2px --focus ring and a 2px offset (−2px in a segment). The "idle" column is interactive. Hover and pressing follow the rule, while the other columns are static snapshots. Change the theme in Tweaks.

Consistency rules
  • Ten button variants and no more (Viewed and Resolve use the same "action toggle" pattern in two colours). Each new button uses a variant from the table instead of choosing a colour.
  • Three weight classes: filled (Primary, Attention, Secondary, Danger solid, Viewed on, Resolve on) use 3 shades of their own colour. Bordered (Ghost, Danger ghost, Viewed off, 25×25 icon buttons, chips) and borderless (quiet mono, toolbar, chevron, inactive segment) share the same grey shades. Active segments and chips do not respond to hover.
  • The trash icon is the one semantic exception. Both the icon and background turn red because the action is destructive.
  • Heights: 29 for composer and floating panel actions, 28 for the top bar, 24 for segments and chips, 23 for Mark viewed and confirmations, 22 for quiet mono, 25×25 / 26×24 / 20×20 for icon buttons. Radii: 7 (h28–29), 6 (h23–25, chips), 5 (26×24 and 20×20 icon buttons), 4 (quiet mono, small segment).
  • Hover does not change the shape. No movement, shadows or scaling. Pressing Secondary solid removes its shadow in the light theme.
  • The same action uses the same variant everywhere: "Cancel" is always Ghost, "Save…" is always Secondary solid, "Delete" is always Danger solid.
  • Three fill meanings: an action uses a neutral fill (--btn-*). An "on" state, with several allowed at once, uses an accent fill (--chip-*). A single choice in a group uses a white item inside a container (--seg-*). A chip does not look like a button, and a button does not look like a selected chip.

2a · 09-20 · №1

"Open issue" toggle in the composer

One row above the editor border: a toggle + the "Open issue" label. An issue is a comment flag on the review host for a remark that must be resolved before merging. The reviewer sets it while writing, and Ship sends it to the host with the comment. For a host without this concept (GitHub, capabilities.issueComments === false), the row is absent. No disabled control or hint. The composer starts with the border.

Decisions
  • Use a switch, not a checkbox or a button: this is a comment property (CommentDraft.issue: boolean), not an action. Ship is the only action. The flag goes to the host in the same batch as the text.
  • The label is two words, "Open issue". Use the host term without explanation. The reviewer knows the concept from their host. Who resolves it and when is a team agreement, which the UI does not describe.
  • Place it above the editor, below the context heading, so the property is read before the text. Below the editor it would compete with "Save draft". Nothing goes on the right of the row.
  • The same row appears in all 3 composer locations (1c, 1d, thread reply), because a reply can be an issue too.
  • A flagged draft has an issue chip next to draft. After publication, the same issue chip stays in the comment header beside the name. It is a flag, not a separate entity. The thread state (open / resolved) works like any other thread. When editing a draft, the switch stays in place and retains its state.
  • Read the host capability once when opening the PR. Without the flag, there is no DOM node. No "unavailable on this host" tooltips.
  • Keyboard: the switch is a tab stop before the editor. Space toggles it. aria-label is "Open issue, off / on".

The edit window becomes a domain decision

EditPolicy now owns the 30-minute dispatch lock. The order model no longer decides editability inline, and the API returns the verdict so clients can disable the control instead of guessing at it.

The policy is only trustworthy if the read path sees the same state — which is the next stop.

02 / 7 high

The cache is dropped after the write, not before it

The old flow invalidated the order cache before saving, leaving a window where a concurrent read repopulated stale state and the client saw an editable order that the write had already locked. A 30-second TTL hid the race in most sessions, which is why it never showed up in the incident log.

Now the write commits first and cache.drop runs inside the same unit of work — a failed save leaves nothing to invalidate. The retry path in retry_edit() still calls drop outside the unit of work; that is the one place where the old ordering survives.

  • order_service.py — commit before drop
  • retry_edit() — drop still outside the unit of work
  • test_order_service.py — new assertion on the failure path

Read the retry path together with the test digest in 04 · What the tests now claim: the weakened assertion there is exactly this ordering.

03 / 7

PATCH validates before it touches the aggregate

Validation order

The endpoint checks the order kind, then the lock window, then the patch body, then the delivery slot, and only after that loads the aggregate.

  1. kind is SCHEDULED
  2. window is open
  3. patch is non-empty
  4. slot exists
  5. slot is in the future
raise HTTPException(409, reason)
headings and code blocks are outside the allowed set. The section goes to route.section again with a lower limit. The UI does not silently truncate text.
Allowed elements and budget · enforced by the validator
  • Allowed: paragraphs (blank line), lists with bullets - or numbers 1., `code`, **bold**, links [text](url). That's all.
  • Forbidden: headings, nested lists, code blocks, tables, images, blockquotes. The diff shows the code, so the description doesn't need it. Numbering is only for lists where order matters (steps, priorities).
  • The budget limits total length only: ≤ 840 source characters (a guideline, check visually on real routes). There is no limit on paragraphs or list items. Three short paragraphs are better than one long one.
  • Lists only enumerate items of the same kind (conditions, files, flags). A paragraph explaining the consequences must follow the list, or the list has no conclusion. Any link is allowed if it helps the review context: files and stops (internal), documentation, issues, dashboards.
  • The bridge phrase and the "why this stop changed" block remain plain text, without markup.

Decisions
  • One message structure at every level: a 24px header (avatar 18 · name · chips · time), 6px, then text below the name (27px). The rhythm stays the same with or without a button in the header. Only the right side of the root header differs, with the Resolve button.
  • Nesting uses only 27px indentation per level (= text column: avatar 18 + gap 9), so the reply avatar sits below its parent's "Reply" link. The limit is 4 (108px). At level 5 and deeper, indentation stays the same, but the header shows "↳ recipient". No vertical lines. The diff already has a line-number grid and a thread edge, and another set of lines would compete with them.
  • Only 12px of space separates messages. The avatar and name already mark the start of each message, so no dividers are needed. Threads have no lines at all, vertical or horizontal.
  • Resolved does not change the block's background or opacity. The button and edge show the status: open has an accent edge 7f8cff, resolved has a grey edge 33383f. There is no separate "resolved by…" badge.
  • "Reply" is a blue link below the text of every message, including the root. The branch grows from the message where it was clicked. There is no separate action row for the thread.
  • Your own messages (published and draft) get muted "Edit · Delete" links in the same row. Other people's messages do not, because hosts do not allow editing them. "Delete" turns red on hover (danger). Clicking it replaces the action row with a confirmation: "Delete comment?" immediately followed by Danger solid "Delete" and Ghost "Cancel" (h23). No modal, and only this row changes. It works. "Edit" opens the editor in place of the text.
  • Status and resolution share one button in the root header, like "Mark viewed" on a stop. When open, it is ghost "○ Resolve" with an amber dot e2954c (open needs attention. Red is already used for deletions and danger in the diff). A click turns it into green "✓ Resolved" (the same tokens as Viewed on). The fill and checkmark show the state, and the verb names the action. Another click returns it to open (title "Reopen"). It works.
  • For a host with per-comment issues (04), status belongs to the message, not the thread. A message with an issue gets an "issue" chip (a boolean flag, as in 2a) and its own ○ Resolve / ✓ Resolved button on the right of the header. Regular replies have neither a chip nor a button. There is no thread-wide Resolve. As elsewhere, the gutter marker shows the message count.

Width · decisions
  • width: clamp(620px, 68vw, 1120px) scales smoothly, like the code panels in spec 09-12. The minimum stays 620 at 1280, and the limit is 1120. A line of 13px text longer than ~760px is unreadable, so the comment body is limited to max-width:760px. The extra space goes to the thread header (chips, actions) and padding.
  • List: max-height: min(60vh, 640px). The composer and header stay fixed, and only the list scrolls, as in 1c. Side padding is 18px instead of 15.
  • Replies stay in place. "Reply" under any message opens the composer directly below it, in its text column, with an issue toggle. "Cancel" collapses it. Replies are always visible when the thread is expanded (threads outside the diff are short). Beyond 4 levels, use "↳ recipient". Shown below the reply from drew.
  • Collapse state: drafts are never collapsed. Bot threads and resolved threads are collapsed by default. There is no separate "collapse all" action or draft counter in the header. Everything is visible in the list.
  • Below a window width of 1280px, the modal = 100vw − 48px. Below a height of 600px, the composer shrinks to 64px (the 1c rule still applies).
