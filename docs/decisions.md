# Decision log

Decisions made during development, grouped by subsystem: what was decided and why. Implementation details live in the code. This log holds only what the code does not explain.

Maintenance: each new decision gets a dated entry in its section. When superseding an old decision, keep its entry. Mark the new one "supersedes the decision of …", and leave the old one as history.

## Session↔server protocol

- **2026-08-19 · Version handshake on every worker request, not just the first `next`.** The CLI stores no state between invocations, and the check costs almost nothing.
- **2026-08-19 · Version compatibility: minor releases break compatibility in 0.x, and matching major versions suffice from 1.0 onward.** The single source of truth is `protocolVersionsCompatible` in `@sherpa/protocol`.
- **2026-08-19 · `taskTypeSchema` is a strict enum.** New task types require a minor version increase. The validator rejects unknown types (fail-closed).
- **2026-08-19 · Worker endpoint paths live in `WORKER_ENDPOINTS` in `@sherpa/protocol`.** Both the server and CLI use them. They are a contract, not an implementation detail.
- **2026-08-19 · RPC error codes map to HTTP statuses through a table in `http.ts`.** unauthorized 401, bad_request 400, unknown_task 404, version_incompatible / lease_not_held / worker_conflict 409, result_too_large 413, internal 500.
- **2026-08-19 · Result limits are 256 KB in the CLI and 1 MB on the server.** The CLI rejects the result locally ("shorten the file and call `complete` again", exit code 1, task stays leased), so the model can retry. The server's `result_too_large` guards against bypassing the CLI. A body over 1 MB is rejected as `bad_request`.
- **2026-08-19 · `prKey` validation uses `prKeySchema` in the protocol.** The alphabet is `[A-Za-z0-9._-]`, and the first character must be a letter or digit. Both sides validate it: the server before creating PR state, and the CLI before inserting it into paths.
- **2026-08-19 · The PR is supplied explicitly through `SHERPA_PR` or `--pr`.** Resolving a PR from the working directory requires a host adapter, so the skill passes the PR itself.
- **2026-08-27 · The harness sets the long-poll timeout.** The desired wait is a worker request field, capped by the server maximum. The worker death deadline is calculated from the requested wait.

## Queue and worker liveness

- **2026-08-19 · A late `complete` gets no grace period.** Leases expire lazily at the start of any operation. A late worker gets `lease_not_held`, claims the same task through `next` (attempt+1), and submits its finished result immediately. No work is lost, and there is no need for a separate "accept from the previous owner" path.
- **2026-08-19 · An empty `complete` result returns `rejected`, and the task stays leased.** This is the minimum fail-closed check until result schemas exist.
- **2026-08-19 · The worker slot is 1 SQLite row per PR, and liveness is computed lazily on reads** (`lastSeenAt + WORKER_DEAD_AFTER_SECONDS > now`). The only timer fires when the worker is due to be declared dead, so "Agent disconnected" appears without incoming requests. In a pending `next`, the server rechecks slot ownership on every wakeup so an old worker cannot take a new worker's task.
- **2026-08-19 · Reconnection means a new `workerId`.** `register` always generates a fresh id. The debugging override `SHERPA_WORKER_ID` is the exception, because otherwise registration and subsequent commands would use different identities and the session would conflict with itself.
- **2026-08-19 · Session identity lives in `~/.sherpa/prs/<prKey>/worker-id`.** An environment variable does not survive separate shell calls from the harness.
- **2026-08-20 · The server writes `worker-id`, not the CLI.** With slot takeover, both parallel sessions receive a successful `register`, so CLI write order would depend on a race between network responses. The server writes the file synchronously in the registration endpoint, keeping write order aligned with slot acquisition order.
- **2026-08-19 · A displaced worker's leases return to the queue as soon as the slot is taken over.** Return semantics match expiration (attempt+1). Status: replaces the 2026-08-19 decision. Previously, leases were left to "expire on their own", which could leave an interactive task waiting for up to 10 minutes after reconnection.
- **2026-08-20 · `register` stays a separate operation and is not built into `next`.** It explicitly says "I am a new session", takes over the slot and returns the previous worker's leases. Registering on every `next` would let a zombie session take the slot back on every call. The asymmetry is deliberate: `register` takes over, and `next` from a non-owner receives "stop the loop".
- **2026-08-20 · The new session always wins.** `register` with a fresh `workerId` takes over the slot even from a live worker. The previous worker's leases return to the queue immediately, and pending polls wake up with `worker_conflict`. Status: replaces the 2026-08-19 and 2026-08-20 decisions. The rule "reject a second live worker", together with the fallback "retry registration using the id from the file", merged parallel sessions into one, with both acting as the worker. Remaining limit: a displaced session that ignores "stop the loop" can read the new id from the shared file. File-based identity does not protect against a deliberately disobedient model.
- **2026-08-20 · Worker liveness treats a disconnected connection as a strong signal and silence as a weak one.** A worker is alive if its worker connection is open, or it holds a lease and has been silent for less than `WORKER_DEAD_AFTER_SECONDS` (6 minutes), or it has been silent for less than `WORKER_GAP_GRACE_SECONDS` (60 s, the gap between loop calls). The server detects a killed idle session in 1 minute instead of 6. A killed session with a lease still takes 6 minutes because the server cannot distinguish "killed with a lease" from "working silently". The grace period is an internal server policy and is not part of the protocol.
- **2026-08-19 · Queue-change notifications use a separate channel from "work available".** The work-available channel wakes long polls, while the UI needs every mutation, including lazy expirations during reads. Notifications go out after the transaction commits and only when something actually changes.
- **2026-08-20 · The server shuts itself down when idle, with no `down` command.** It is busy while at least 1 connection is open (a UI tab or pending poll), or less than 15 minutes have passed since the last incoming request. Internal timers do not count as activity. Shutdown follows the same path as SIGTERM: the server removes the manifest and logs the reason in `server.log`. The timeout is disabled in development mode.
- **2026-08-27 · There is no "Agent disconnected" banner. The status lives in the agent indicator,** and its popover explains that "the reader remains fully functional, and marks and drafts are saved". This reverses the corresponding design handoff item.
- **2026-08-31 · `done` when the UI leaves.** The server returns `done` when the UI has connected before, has been absent for longer than `UI_GONE_GRACE_SECONDS` (60 s, since reloads, sleep and brief network interruptions break connections for seconds), and the queue has no open tasks. Closing a tab does not interrupt generation already in progress. The server never returns `done` before the UI first connects, and a returning tab restores presence. There is no machine-readable reason field because the harness behaves the same for every reason, and text is enough for the person.
- **2026-09-02 · A task cancelled while leased stays "with the worker" until its next request.** Its status becomes `cancelled`, but the holder and lease deadline remain until the worker responds, the lease expires or the worker is displaced. The UI therefore shows that the agent is still busy with the cancelled task. Generation does not count this holding state as an open task, so it does not block a new run.

## CLI and skill

- **2026-08-20 · The skill knows the minimum, and `sherpa up` handles all bootstrap work.** The worker model does not need architecture, requirements or protocol steps. `up --pr` finds or starts the server, registers the worker, and prints the UI link and loop instructions. SKILL.md has 2 steps: `up`, then the `next` loop.
- **2026-08-20 · Skill installation symlinks the package directory into the harness's skills directory** (`~/.claude/skills/sherpa`, `~/.codex/skills/sherpa`).
- **2026-08-20 · Distribution: a standalone skill, a `node:sqlite` server, 2 bundles.** Switching to built-in `node:sqlite` removed native dependencies. The server builds into one `sherpa-server.mjs` with embedded UI assets (from disk in development, through a shared static-source abstraction). The CLI stays a separate thin `sherpa.mjs`, since the loop invokes it on every call and startup must be fast. Distribution = SKILL.md plus `bin/{sherpa.mjs,sherpa-server.mjs}`, with no checkout or pnpm at runtime, requiring Node ≥ 22.13. Supersedes the 2026-08-19 decision that the skill ran only from a repository checkout.
- **2026-08-20 · `--harness` and `--model` are free-form display strings.** Actual values vary (`claude-opus-5[1m]`, `gpt-5`), so there is no allowlist check. The CLI trims quotes and whitespace and truncates to 64 characters, the server stores the values as received, and the UI shows "Agent · harness · model". Registration renewal updates the labels, and taking over another dead worker's slot resets them.
- **2026-08-20 · Everything model-facing is in English, everything reviewer-facing is in Russian.** English SKILL.md also requires English CLI output and server worker text, otherwise the skill would refer to Russian loop phrases. The markers "stop the loop", "No tasks", "DONE" form a contract between SKILL.md and code, enforced by a test that looks for SKILL.md phrases in the built bundles. UI, `server.log`, dev scripts and code comments are Russian.
- **2026-09-01 · The distribution version is a single `version` field in the root `package.json`.** There were 3 unsynchronized versions (CLI, UI and a hardcoded server version), while `--version` printed a placeholder. The first numbered release is `0.2.0`, since `0.1.0` is already used in the history of the server constant. `PROTOCOL_VERSION` tracks compatibility separately and is not tied to the distribution version.

## Host adapters

- **2026-08-20 · The diff and all PR data come from the REST API, with no checkout needed to read them.** The entire patch arrives in one request in half a second.
- **2026-08-21 · Fixtures live in a separate `@sherpa/fixtures` package.** It has 2 consumers, server contract tests and the browser state gallery, so the package has no Node APIs and depends only on `@sherpa/protocol`.
- **2026-08-21 · UI lens labels are defined by lens ID, with the host label as a fallback.** The UI labels known IDs (`mine`, `pci`) itself. An unknown lens from a future host uses the host's label. Filters are extensible and must neither crash nor disappear.
- **2026-08-27 · A lens with zero files in this PR is not rendered at all**, either as a chip or as a select option. The PCI chip in the header and the audit banner use the same visibility rule. Supersedes `docs/design/SPEC-elements.md §4.2` for empty lenses.
- **2026-08-27 · The ownership lens is always visible.** Hiding lenses with zero files applies only to other lenses. With no owned files in the PR, "My files" is visible and disabled with an explanation, just as it is when there is no ownership zone.
- **2026-09-03 · "Open in external editor" is removed from the product, along with its endpoint.** PR files are not available locally, so there is nothing to open. The file link points to the host, with `hostFileUrl` alongside `blameUrl`.


## Diffs and images

- **2026-08-20 · Diffs travel as raw per-file unified diff (`FileDiff.patch`), and only the UI worker parses them into a line model.** The adapter and server do not interpret patch text.
- **2026-08-21 · The adapter counts review host diff statistics from the patch body.** The change list has no ready-made statistics. A rename in the source patch is a pair of blocks, "delete old path, add new path in full". The adapter takes the new-path block, so a pure move shows "+N/−0". The actual delta requires a separate text-diff request.
- **2026-08-22 · For context expansion, the host returns the entire file contents, and the UI computes the expansion.** An optional `ReviewHost.getFileContent(fileId)` → `{oldText, newText}` and `capabilities.fileContent` replace a context-width protocol. Context lines are identical in both versions. The UI fills gaps itself and gives the trailing gap its actual length.
- **2026-08-27 · The ±20 step belongs in gaps between hunks, and the file card header button expands the entire file.** Supersedes `docs/design/SPEC-elements.md §2.13` for the ±20 button.
- **2026-08-28 · Loaded context is not persisted.** Expanded gaps live in tab memory. Context provides a view around changes rather than review progress, and does not change file read status.


## Route

- **2026-08-25 · The route snapshot contains only model output. The UI calculates derived data.** The snapshot contains the plan (id, number, tier, title), stop content (paragraph, bridge, anchors, test digest, dropped assertions, validator notes), summary, traversal order and provenance. The UI derives file chips, counters, coverage fractions and the contents of "Other" from anchors and its own diff model. The snapshot has no derived fields, so they cannot drift out of sync. The model places anchors by file path, and the validator converts them to `fileId`.
- **2026-08-25 · "Other" is a synthetic stop added by the server when it accepts the skeleton** (the last plan number, status "ready"). The UI hides it when there are no uncovered lines. Promoting it when its share exceeds 40% changes the rendering order, while numbers stay fixed by the plan.
- **2026-08-25 · Generation phases are `none/reading/filling/ready/failed`. The summary arrives in full with the skeleton.** There is no token streaming in the polling loop, so the handoff's promised "streaming Summary" becomes a placeholder until it is ready. A section failure is the status of its stop, not a phase. "The agent died during generation" is not a phase either. The UI combines `filling` with worker status. Route text is in Russian because the reviewer reads it, and prompts are in English.
- **2026-08-26 · A section failure does not fail the route.** The `failed` phase applies only to the skeleton. A failed section gives its stops `failed` status with a note, and the route reaches `ready` with unfilled slots. Cancelling the skeleton from the UI sets the phase to `none`, meaning "stopped", not "broken". `contentHash` is calculated from model content without service fields, so the same route from different sessions produces the same hash.
- **2026-08-26 · Generative results go through a synchronous acceptor inside the `complete` transaction.** A cache in the orchestrator separates asynchronous diff reads from acceptance. Accepted results are applied through a callback after commit, with no nested transactions. Rejection does not consume an attempt or release the lease. The budget is 3 rejections per lease, after which the task becomes `failed` with the last raw output. A third outcome, "nothing to validate against" (the diff is still loading after a restart), does not consume the budget.
- **2026-08-26 · The orchestrator is a reconciliation-driven state machine, not an event-driven one.** On every queue change, it recalculates stop statuses and phase transitions from queue state. The same code handles server restarts, agent death and session displacement without special branches. Skeleton rescheduling is limited to three tasks. Sections are queued in plan order and accepted in arrival order without buffering. The first result submitted wins a range conflict.
- **2026-08-26 · Generation context is passed as files, with line numbers in the patch gutter.** A task carries a short pointer (less than 500 bytes) and file paths: guide, PR context, result schema. The same traversal that the validator later uses to accept anchors numbers both sides of the patches, so printed and validated numbers match by construction. The model doesn't count lines from the hunk header. The context budget is 320 KB. The full changed-file list is never truncated (the coverage rule). Patches are truncated instead, generated files first, then the largest, with test files last in section context.
- **2026-09-02 · The server writes context shared across tasks to disk once, under `payload/shared/`,** keyed by its content. The rule "read files under `shared/` once per session" lives in SKILL.md and task instructions. Previously, five questions about one PR meant reading the same diff five times, at up to 80k tokens each. Tasks remain self-contained. The file is on disk, the path is in the task, and a new session reads it as usual.
- **2026-08-26 · Section batch size stays at one because progressive delivery matters more than latency.** Measurement on a real PR: 403 s from queuing the skeleton to completion. One task for all sections takes 294 s (−27%), but everything arrives at once. The "≤ 90 s" budget is unreachable with the current generation of models. The skeleton alone takes 77–97 s.
- **2026-08-31 · The voice validator rejects only clear violations:** emoji and six filler phrases in reviewer-facing text. Superlatives are not on the stop list because they cannot be distinguished without morphology, and a false positive wastes a model attempt on a style complaint. Subjective style rules stay in the guide. The worker is told directly: the server validates the schema, do not validate it yourself, always submit.
- **2026-08-26 · Changed whitespace-only lines do not need route coverage.** Empty separators between blocks belonging to different stops regularly appeared as "not placed". A changed line containing only whitespace and not covered by an anchor is excluded from coverage statistics entirely. It appears in neither "Other", the hatch nor the percentage denominator. An anchored line counts as before. The server and UI use the same rule, so their numbers match by construction.
- **2026-08-26 · The route in Full diff is a lightweight "file → stops" map that needs no patch parsing,** so badges appear immediately. This layer renders only in the `ready` phase. During `filling`, "not placed" cannot be distinguished from "not filled yet", so the numbers would be wrong. The same helpers calculate uncovered ranges for "Other" and the coverage bar. A file in multiple stops gets the badge of the first stop in plan order and "+N".
- **2026-08-26 · The UI does not revalidate raw skeleton output.** The handoff hint "fix the anchors and revalidate" does not apply. The `failed` phase occurs only for the skeleton, and its output schema has no anchors, so there is nothing to fix. The UI shows raw output as is.
- **2026-08-27 · The digest hides only test files belonging to its stop.** Assertion anchors pointing to files outside the stop are valid input, so the server stays unchanged. If there is no overlap, the toggle is omitted entirely. A link row says "test code is in stop NN" or "in Other" instead. If there is nowhere to link to, there is no row.
- **2026-08-31 · Filling a single stop uses the regular `filling` phase.** The endpoint queues the stop, and existing reconciliation handles the rest. Full regeneration is unavailable during this time because filling is brief, and the banner explains the state. The snapshot identifier in the request body prevents a race with snapshot replacement, because stop ids are not stable across snapshots.
- **2026-08-31 · Regeneration is available from `ready`.** The "worth regenerating" banner must offer an action. Regeneration leaves everything intact until a new skeleton is accepted. The old snapshot stays visible and readable during `reading`/`filling`. Progress is cleared and the snapshot replaced in one transaction at acceptance. Cancellation and failure restore the old route as it was. Status: supersedes the decision of 2026-08-26 under which `generate` from `ready` responded "already in progress".
- **2026-09-02 · The small-PR threshold counts only lines:** additions plus deletions ≤ 40. The "or files ≤ 1" condition is removed because it left every single-file PR without a route, even one with five hundred lines. The invariant is in `docs/architecture.md §7.6`.
- **2026-09-04 · The server deterministically recalculates the generation cap when accepting the skeleton** and stores it in the PR database. It is not carried in a task or lost on restart. Conflicted files are excluded from the route model on input, otherwise the sum of coverage-bar segments would disagree with the denominator.
- **2026-09-09 · Context expansion in a stop slice skips changed lines belonging to other stops.** Expansion used to stop at the first changed line of another stop. For a gap starting with such a line, the ↑/↓ targets appeared but did nothing, while the counter promised unchanged lines beyond it. The ±20 step now counts only unchanged lines. Changed lines belonging to other stops stay hidden in a separate gap labelled "N changed lines in other stops", just as in full-file expansion. A single slice gap can now split into several gaps with one expansion key. The remainder for that key (both unchanged lines and changed lines from other stops) is summed across all pieces, and the row's React key also includes the piece boundaries. A related dead click is fixed in the same place. When a slice merges with a real bridge in the model and hides only changed lines from other stops, the bridge gets the key, because there was nothing to expand under the slice key.
- **2026-09-04 · Filled stops do not show validator notes.** Seven lines of "anchor dropped: nothing changed in this range" took up card space, while the reviewer cannot move an anchor anyway. Missing coverage is visible in the bar and in "Other". Notes still go into the snapshot as a generation audit trail, but render only on an unfilled stop, where they explain the empty slot. This deliberately departs from `docs/design/SPEC-elements.md §4.3`.
- **2026-08-26 · Decisions for generation states:** "Other" counts as a ready slot in "N of M ready" (it can already be read). Small PRs redirect to Full diff once, and only before the reviewer explicitly chooses a view. Promoting "Other" and the "consider regenerating" banner stay silent during `filling`, because uncovered ranges in an unfinished route are unfilled plan slots, not the model's final judgment. The agent indicator counts any open task as work. The summary renders as plain text, with no Markdown renderer.

## Reading progress

- **2026-08-22 · Progress records represent only explicit actions. The UI interprets defaults.** A file record appears after a reviewer action. An absent record means the default calculated by the UI (generated files count as viewed). The server does not interpret patches. The record is mirrored to the host after the local write, without guarantees. A mirror failure neither rolls back the record nor counts as an endpoint error.
- **2026-08-31 · Viewed state has three values: `true | false | null`.** `null` means "the reviewer has made no decision, and the record exists for its ranges". An explicit clearing of the mark and a synthetic record for a file with only stop ranges used to look the same on the wire. As a result, marking a stop that touched a generated file removed its default. The UI heuristic "`false` with nonempty ranges does not mean clearing the mark" was rejected because it loses an explicit clearing in the sequence "clear the mark, then mark the stop". Clarifies the decision of 2026-08-22.
- **2026-08-26 · For stop progress, the UI calculates ranges and the server stores them against the stop.** The stop mark and its files' seen ranges are written in one transaction. The server does not interpret ranges because it has no diff model of its own. Clearing a mark removes only that stop's ranges. Other stops and manual file marks stay unchanged. New route generation clears stop progress and its ranges, while file marks survive.
- **2026-08-31 · A file becoming viewed through coverage is mirrored to the host.** The UI sends deltas after recalculating ranges, without a local record or a new revision. The first snapshot is the baseline, so opening a tab does not replay history. The generated-file default, partial progress and explicit file marks are not duplicated. Status: supersedes part of the decision of 2026-08-26. "Stop marks are not mirrored to the host" still holds for the stop record itself.
- **2026-08-26 · The "show test code" toggle writes no progress, while marking a digest stop also marks its test files.** Reading without a mark is not tracked at all. The digest stop's anchors are the test files themselves, and their assertions are the contract. Otherwise "the diff you actually saw, 100%" cannot be reached in the intended flow, because test code is hidden by default.
- **2026-08-27 · A stop is marked automatically when coverage changes from "uncovered → covered".** The first calculated snapshot is the baseline, so loading server progress on opening does not look like a reviewer action. Clearing a mark by hand blocks automatic marking until coverage is lost and restored, otherwise automatic marking would immediately undo the clearing. The server handles the symmetry "clearing a file also clears its stops". Only the server knows the "stop → ranges" relation, so this also works from Full diff.
- **2026-08-27 · A stop with an unparsed file or a file whose parsing failed cannot be marked:** the toggle is disabled, a tooltip gives the reason, and a button retries parsing. The option "allow the mark but leave the failed file uncoloured" was rejected because ranges are written once when the mark is set, so the file would stay unread forever. The cost: stops cannot be marked when the diff worker is dead, which is more honest than silently losing progress.
- **2026-08-27 · Progress revisions are checked for inequality, not treated as monotonic.** They are monotonic only within one server lifetime, which is why the progress snapshot stopped being reread after a restart.
- **2026-08-27 · Marking a stop collapses it and scrolls to the next entry in the current preset**. Scrolling follows collapse, not a stepper. The last stop does not request scrolling. Clearing a file mark clears its stop mark too, for symmetry.
- **2026-09-02 · The same rule extends to files.** Marking the file the reviewer is reading scrolls to the next file in the current order and filter. It chooses the nearest expanded file below, or simply the next file if everything below is collapsed. The target's collapsed state stays unchanged. Clearing marks and noninteractive changes (server events, progress rereads, coverage from stops) do not request navigation. Only the reviewer action handler queues it. Continues the decision of 2026-08-27.

## Comments and publishing

- **2026-08-24 · Thread writes use REST endpoints over the host's write methods, with state converging through events.** Saving a draft returns the created comment (the composer needs its id for editing and deletion). The other endpoints return an acknowledgement without data. A successful write increments the thread revision. The UI gets the source of truth by rereading the endpoint and uses optimistic state until then. An extra read when polling detects the same write is cheaper than teaching the feed to distinguish its own writes from someone else's.
- **2026-08-25 · Publishing uses one endpoint over `publishBatch` and returns its result unchanged.** There is no progress stream. A batch has only a handful of comments, and publishing makes one host call. Any failure means the verdict is treated as not applied. The review is unfinished, and the UI offers a retry. The "Review complete" screen is tab state after successful publication, with no server persistence. After a reload, the host's PR status is the source of truth.
- **2026-08-31 · Drafts are saved only explicitly.** Typing changes composer state. The button or ⌘⏎ starts the write. After saving, the input closes and the draft stays as a card. Editing it again requires an explicit action. The browser shows its standard confirmation when leaving a page with unsaved text. Text is not written to `localStorage`. This cancels autosave from `docs/design/SPEC-elements.md §2.17`.
- **2026-09-03 · The draft buffer stores composer state instead of a phantom comment, with `clientKey` making retries safe.** A buffered record is text in an open composer at its anchor, with the status "we'll save it when the connection returns". It does not enter the thread store, polling does not remove it, slices have no phantom comments, and reloading opens the composer on the same line. The UI sends `clientKey` with every write. The server overwrites the previous record by that key and calls the host with the same idempotency key. The delivery process retries after 10/30/60 s. Buffered records count as drafts and block publishing. Status: replaces the 2026-08-24 decision under which the first save was not idempotent and the composer warned "retrying may create a duplicate" instead of retrying automatically.
- **2026-08-28 · The composer uses an existing ProseMirror editor instead of a custom contentEditable.** Guaranteed markdown round trips matter more than another custom subsystem. "Visual" is real input, not a preview, and losing `**`, backticks, lists or links would lose the reviewer's text. The dependencies are `prosemirror-{model,state,view,keymap,history,commands}` and `prosemirror-markdown`: MIT, no postinstall scripts, no React binding needed. The editor loads as a lazy chunk (325 KB, 115 KB gzipped) because the composer opens rarely and the UI bundle is embedded in the server. The store's source of truth is markdown. Other people's content keeps its own safe renderer. Two markdown stacks side by side are a deliberate cost.
- **2026-08-31 · Literal markdown is parsed on paste and when an inline marker closes.** Clipboard text goes through the same parser as switching editor modes. `**x**`, `*x*` and `` `x` `` become formatting after the closing marker. The rules do not run inside code.
- **2026-09-02 · Block input rules turn `- `, `* ` and `+ ` into list items, `1. ` into a numbered item, and triple backticks into a code block.** Backspace immediately after a rule fires restores the literal text. Enter in an empty item exits the list. Tab and Shift-Tab nest and lift an item. This adds `prosemirror-schema-list` because the base command set knows nothing about lists, and implementing item splitting and lifting by hand would rewrite the canonical module. Input rules do not create headings or blockquotes. There are no buttons or styles for them, so the resulting block would have no visible representation or way to remove it.
- **2026-08-31 · The "Comments on the PR" modal contains human PR-level threads, not everything outside the diff.** PR-level means no anchor. The list includes those threads' root comments, both published comments and the reviewer's own drafts. Replies do not expand in the modal. Bot threads and threads anchored to files that disappeared stay in the Overview's "Discussion" card. They must not be duplicated as a wall of text in the modal.
- **2026-09-04 · The "Discussion" card also shows human PR-level threads.** The modal remains where reviewers write them, and the card is where they see them. Clicking a participant sets an author lens for threads in Full diff (tab memory). Overview does not navigate to a specific thread. Participants sort by open-thread count, with bots after people. Status: replaces part of the 2026-08-31 decision.
- **2026-09-01 · "Turn into a comment draft" on a note opens a prefilled composer instead of saving a draft:** nothing goes to the host until an explicit save. The initial text is the line "Quoted from the agent's answer:", a blank line, and the note text as a blockquote. The attribution is editable as ordinary text. The draft anchor covers the note's entire range.
- **2026-09-04 · An image comment has a file anchor without a line.** The "Comment on the file" item appears only in image card menus. The composer distinguishes PR, file and range levels.
- **2026-09-03 · "Someone shipped first" comes from the overall PR status and the reviewers list in metadata,** both of which fit in the same cheap poll. The banner appears when someone else's ship is observed. Its time starts at observation because the API has no timestamp. Unresolved threads do not block publishing. They only appear in the summary. Drafts do block it.

## Chat and notes

- **2026-09-01 · The chat data unit is an exchange (one record for a question and answer), not a sequence of messages with roles.** Status (`queued/running/done/failed/cancelled`) lives in one place. An "answer without a question" is not representable, and cancellation and retry address one entity. The UI expands the exchange into the chat timeline.
- **2026-09-01 · An answer arrives in full when one task completes, as markdown without a schema.** The polling loop has no token streaming, so the streaming promised by the spec becomes an answer indicator and progress lines. Only structured tasks have a result schema. The shared 256 KB limit applies. The voice validator also checks chat answers because the reviewer reads them.
- **2026-09-01 · The server creates a note in the answer-acceptance transaction, with a copy of the answer as its text.** A note is self-contained and lives and is deleted independently of history. The link is one-way through the exchange id, and the "pinned" mark is derived and clears itself. The anchor carries a path alongside `fileId`, so the chip label survives the file leaving the diff. Collapsed note state stays in tab memory without persistence.
- **2026-09-01 · Cancellation works for both queued and leased tasks.** The worker learns about it on its next CLI call. Retry queues a new task for the same exchange.
- **2026-09-01 · "Ask the agent to place them" puts a question in the composer for the reviewer to send.** All entry points only prefill text. A question has one anchor. "Other" goes without an anchor and lists ranges in the text (the first 20 and "and N more"). A hatched bar sends an anchor for its own range. The button does not change the route: "the answer will arrive in chat, and the route will not change".
- **2026-09-01 · Generation, regeneration and filling remain available when the agent is disconnected:** the queue is durable, and tasks will wait for the worker. Only chat entry points lose functionality. The reader is always available.

## Iterations

- **2026-09-02 · The unit of time is a host iteration, with a separate `watchIterations` subscription returning the full list on change.** Threads and iterations have different consumers, so this does not extend `watchThreads`. The adapter does not return "gone" status. The server assigns it by comparing the host list with its own storage. `capabilities.iterations` means "the host lists previous iterations and returns a slice between them".
- **2026-09-02 · The tab's selected view is a client choice in the URL fragment.** Endpoints take an iteration or slice as parameters. The server has no "being viewed" state. The UI derives read-only mode from "selected iteration ≠ active iteration". `getDiff` accepts only a complete slice `{base, head}`, with no more half-specified requests.
- **2026-09-02 · "New / changed" classification uses section anchors (already converted to `fileId`), and marks carry over when the snapshot freezes.** The skeleton has no anchors, so earlier classification has no data to use. Until freezing, "N of M carried over" stays hidden to avoid a false "0 of 7" on the second pass. The model writes the reason for a change, and the server assigns its kind. Other values are discarded with a note.
- **2026-09-02 · Stale-route state is computed by a separate feed at the read boundary instead of being stored.** The route revision for the UI is the sum of the storage and feed revisions. Affected stops arrive in a second notification after the interdiff. The generation diff is tied to the task's iteration. A push during generation does not move it.
- **2026-09-02 · Progress carries over between iterations once per "source → destination" pair,** and this is recorded so a mark cleared after carryover does not return. A file's "viewed" mark carries over only for unchanged files. Explicit clearing always carries over. A force-push loses progress from a vanished iteration because the host cannot compute a slice against it.
- **2026-09-03 · The carryover source is found through progress records instead of the iteration list.** Only iterations that were active on recent versions have a list entry, so older progress was silently lost. The "`fileId` → path" map no longer depends on a stored patch because progress records store the path themselves. If neither the host, patch nor snapshot knows the source base, the active iteration's base is not substituted. A conservative mode treats the old side as affected because substitution silently produced an incorrect line map.
- **2026-09-03 · Host failures on a slice have the same classification for notes, progress and affected stops.** A vanished iteration or the host's `bad_request` is permanent. The source is marked as rejected, notes mark their anchor as lost while retaining the original, and progress moves to the next source. Everything else is temporary, with a retry after 30 s. Progress does not move to an older source on a temporary failure because a network failure must not silently downgrade the source.
- **2026-09-03 · The tab's diff follows the route snapshot.** While the snapshot describes a previous iteration, the tab stays on its diff (anchors address files by their iteration's `fileId`) and moves to the new one when a new skeleton is accepted. Previously, after a push the tab kept the old iteration's files while the route arrived with the new iteration's anchors.
- **2026-09-04 · The second-pass banner reports two things separately:** how many stops remain viewed and how many changed. The denominator includes only stops with anchors, excluding the synthetic "Other". When nothing carries over, the server gives one of three reasons: the source had no marks, marks existed but covered no complete stop, or the host did not return a slice. Counting carried-over destination lines cannot work because regeneration within the same iteration has no line carryover, which always produced "there were no marks".
- **2026-09-03 · A snapshot of an iteration lost to a force-push stays current, with editing enabled, for as long as it is the current snapshot.** "The commit is no longer in the PR" and the editing restriction appear after rebuilding for a new iteration.

## Server and storage

- **2026-09-09 · Set the server listen address with `SHERPA_LISTEN_HOST`.** The default remains `127.0.0.1`. A value of `::` allows direct IPv6 access to the VM and preserves the CLI's local IPv4 connection. The manifest stores the UI URL address, so repeated `sherpa up` calls show the same link. Token checks remain in place. Direct HTTP access is unencrypted. Changing the address requires a server restart.

- **2026-08-19 · The UI channel uses SSE, with a complete state snapshot on every change.** WebSocket is unnecessary (dependencies and manual reconnection), and granular events do not pay off because the queue is small. A tick every 30 s sends a fresh snapshot and also lazily expires leases when nobody calls the server. The UI↔server contract also lives in `@sherpa/protocol`, and the UI validates every snapshot with fail-closed behaviour.
- **2026-08-19 · Events take the token as a query parameter, while static assets need no token.** EventSource cannot set headers, so only the events endpoint accepts `?token=`, with the same constant-time comparison. Static assets contain no secrets. The token arrives in the URL fragment and never reaches the server. All `/api/*` endpoints require a token.
- **2026-08-21 · Heavy review data uses separate GET endpoints instead of the snapshot.** The diff and threads weigh megabytes and cannot enter every tick's snapshot. The event carries only a monotonic thread revision, and the UI rereads the endpoint. Error codes are `no_review_host` (404) and `host_unavailable` (502).
- **2026-08-20 · The server sweeps expired manifests for other PRs only on an actual start.** Walking the manifest directory was kept out of the thin CLI. The directory cleans itself on the next cold start.
- **2026-08-21 · IBM Plex fonts come from npm packages and are vendored by the build.** Files enter the bundle, with no runtime network access and no binaries committed to git. The workspace has `allowBuilds: false` because these packages' postinstall scripts are telemetry and must not run.
- **2026-08-21 · UI development pages, the state gallery and demo, stay out of the production bundle,** because otherwise fixtures would enter the server bundle. In development, `/api` is proxied to a running server using the manifest, with an ephemeral port.

- **2026-09-10 · Feedback issues have no parent.** Previously, they were subtasks of #2300. Sherpa now has its own issue destination, and a tree of subtasks under one issue made feedback harder to triage. The `SHERPA_FEEDBACK_PARENT` and `SHERPA_FEEDBACK_QUEUE` variables and the request's `parent` field were removed. There is one hardcoded destination. The unavailability message now points there instead of to an issue.
- **2026-09-02 · Per-PR UI state is a key-value table in the PR database, with one endpoint and whole-field replacement.** The contract schema defines the fields. Adding a field requires no migration, and a corrupt value falls back to the default for that field alone. Merging by key cannot represent the data because maps store explicit reviewer choices, and "restore the directory default" deletes a key. Writes are optimistic, delayed by ~300 ms. A closing tab flushes pending writes with a `keepalive` request. A failed initial read disables writes until reload. State stays in tab memory, and server-saved state remains intact. This removed the last `localStorage` use from the production UI.
- **2026-09-03 · New-version checks only notify.** The server compares the distribution's `version.json` with the published version and adds an update to the snapshot when it is newer than the current version and has not been dismissed. "Later" lives in tab memory. A failed recheck neither erases a known version nor enters the cache, otherwise one failure would hide the toast for half an hour. The response omits the failure reason. It goes to server stderr, and the UI has no use for the distinction.
- **2026-09-04 · The update toast sits above the floating action panel.** On a wide PR, the panel reaches the left corner and would cover the toast buttons. The toast's Esc handling stays a local listener that works only with focus inside. It is not a layer in the shared stack, because a layer would dismiss the toast from anywhere.
- **2026-09-03 · Old iterations are not cleaned up, and no local event telemetry is collected.** After four stages, `~/.sherpa` uses 28 MB for 21 PRs, at most 3.1 MB per PR, so there is nothing to clean. Aggregated events from one user do not answer behavioural questions, and there is no event sink.

## UI: keyboard, palette, i18n, onboarding, settings

- **2026-09-10 · Theme is a global `dark | light` setting, defaulting to `dark`.** The toggle is available in the top bar on every screen. The choice lives in the shared `settings.json`, so it survives server restarts and opening another PR on a new port. `localStorage` does not work for this. The existing dark appearance remains the default, unaffected by the OS theme. The light palette overrides color tokens at the document root, including the diff, syntax, portals and native controls. Geometry stays the same. The new schema field has a default for older settings files and does not change the worker task protocol.


- **2026-08-22 · Side-by-side mode measures width from the card list's padding box** (`clientWidth`), not the window. A 290px tree panel sits to the left of the list. Page padding counts as space allocated to the diff, not an external frame.
- **2026-09-02 · The minimum window width is 1280px.** The handoff's 1440 threshold caused horizontal scrolling on a typical laptop because the layout overflowed the window instead of shrinking. The full gallery was checked, none of its 148 states overflows. The trade-off is accepted. At 1280, the card list has 989px, so side-by-side mode (threshold 1100) is always disabled and becomes available at a window width of ≈1391px. The 1100 threshold stays because 2 code columns really are cramped at 989px.
- **2026-08-27 · Design handoff changes after the first reviews:** Overview is always the initial view because the route is never ready as soon as the PR opens. The floating action panel appears in all views, not just diff views. When scrolling Full diff, the PR header scrolls away and a compact toolbar strip stays sticky. Long lines wrap, with no horizontal scrolling or toggle for it. The composer gets visible "Save draft" and "Cancel" buttons alongside the shortcuts. "Copy link" and "Open in editor" leave the file card header, and "Copy stop link" leaves the stop header.
- **2026-08-27 · There is a gap between the sticky stop header and the route toolbar.** This deliberately departs from the mockup, where they touch and merge visually while scrolling. The toolbar height is no longer a constant. The component measures it so toolbar changes cannot silently get out of sync with the sticky offset.
- **2026-09-03 · The floating panel is centred on the content column,** and its shortcuts are disabled under the chat overlay's scrim too. Publishing through an invisible button must not be possible.
- **2026-08-27 · A custom Markdown renderer produces React elements, without `innerHTML` or external dependencies.** Content comes from outside (host comments, model text), but no separate sanitization layer is needed because raw HTML stays literal text. Links allow only `http`, `https` and `mailto`, other schemes render as text. There are 2 narrow profiles. A custom parser handles less than a third-party sanitizer would. The comment profile supports lists, code, emphasis and links. The route profile supports only inline code in backticks, everything else is literal.
- **2026-09-03 · Markdown headings in comments have distinct levels:** `h1`–`h3` use higher steps of the existing token scale (the handoff gives no sizes for heading levels), while `h4`–`h6` stay bold at the same font size. Tables are the only place with horizontal scrolling because they cannot wrap.
- **2026-09-02 · Global UI settings live in `~/.sherpa/settings.json`, not `localStorage`.** Each PR (and each restart) has its own port, hence its own origin and empty browser storage. The diff mode used to reset with each new PR. Three scalars don't justify a second migration chain, so this is a plain JSON file with 0600 permissions and atomic writes. PATCH rereads the file before merging because servers for different PRs write it concurrently, and a blind overwrite would erase another server's changes. The first render waits at most 1.5 s for settings. Otherwise the mode toggle visibly switches and the editor is recreated while the reviewer is already typing. A change in one tab reaches another only after a reload. Nested settings objects (onboarding, updates) are replaced as a whole in a patch, not merged by key.
- **2026-09-03 · UI language: explicit setting → agent label → browser.** People who write and read Russian often have English as their browser language, while the agent sees the actual conversation. The explicit setting takes priority over the agent because it is a direct user action. The skill supplies the hint (`sherpa up --lang ru|en`, "if unsure, omit it"). It travels as a third session label beside `--harness` and `--model` and follows the same rules: re-registering without the flag does not erase it, and a new session with a different flag updates it. There are 2 languages, and everything other than `ru` counts as `en`. A language change is a worker status event. In auto mode, the UI rerenders without a reload. Protocol 0.10.0.
- **2026-09-04 · The route language is the UI language when generation starts.** The server selects the locale (request body → setting → agent label → `en`), and the whole snapshot uses one language. When it differs from the current UI locale, the provenance indicator shows the language and a lowest-priority "rebuild?" banner appears. There is no automatic rebuild. The generation locale is stored in the PR database because the skeleton task survives a server restart, and acceptance must allow it in the prompt's language.
- **2026-09-04 · The onboarding tour starts on first open, without waiting for a route.** While there is no route (generation is running, the agent is disconnected, generation failed), the UI draws a tour scaffold on the Route tab for the steps to attach to. The scaffold disappears when the real route arrives. Waiting for the first PR with a route would leave a new user staring at an empty screen without explanation. If the tour is incomplete, the initial view is Route unless the URL fragment specifies one. The tour itself never switches views. The agent step is omitted if the agent is disconnected at the start, and reconnecting does not restore it. The early idea of waiting for the first filled stop is cancelled. The departure from `docs/design/SPEC-onboarding-2026-09-02.md §5` is deliberate.
- **2026-09-03 · Each palette command has a scope (`global | route | full-diff | overview`) and a section.** The palette searches the active scope's commands first, then global commands. The palette and shortcuts sheet see the same set. Esc dismisses the palette, modal, popover, toast, selection in that order, one layer per press, including in input fields. The composer and tree filter stay local because cancelling input is not an overlay action. The first key of a chord is intercepted for a second. An unrelated key cancels the chord and is then handled on its own.
- **2026-09-04 · `@` in the palette searches chat history, rather than filtering threads by person.** The spec contradicted itself. Threads by person are available through the lens on Full diff, and there is nowhere else to search chat history. Search is client-side and matches substrings because the endpoint already returns all exchanges for the PR. An exchange's anchor is live if the anchor file exists in the iteration being viewed.
- **2026-09-04 · The file menu uses the handoff's tokens because there is no prototype for it.** Disabled items stay visible and dimmed with a tooltip so the menu doesn't jump. Keys inside the menu don't bubble, except Esc, which goes to the shared dismissal order.

## Performance and tests

- **2026-08-19 · The CLI bundle is built once per test run, in global setup.** esbuild overwrites the file non-atomically, while test files run in parallel processes. Building in each one caused a race that could read a truncated bundle.
- **2026-08-25 · E2E is a separate Playwright package, outside the standard checks.** Browser tests are slow and can be flaky, so runs are explicit. There is one browser, chromium from the user cache, with no system installations. Each run gets a fresh temporary state directory (the reviewer's `~/.sherpa` is untouched) and the real built UI.
- **2026-08-25 · The frame-time budget on the large fixture is a mean ≤ 16.7 ms and p95 ≤ 33 ms** during programmatic scrolling in headless chromium. This gives twice the margin over the measured 2.3–5.4 ms so runs don't become flaky on a slow machine.
- **2026-09-03 · Performance is measured by intervals between frames, not just the cost of work within a frame.** On a route of 25 stops, the previous method reported 0.08 ms and looked perfect, even though the frame exceeded 16.7 ms. The 149 thousand DOM nodes cost the browser time, outside our code, and were absent from the measurement. The old series stays because it shows our share. The measurement covers 76 files out of 100 because cards collapsed for a reason do not request parsing.
- **2026-09-04 · Heavy routes shed work by unmounting a stop's diff column, rather than virtualizing individual lines.** The section, narrative, chips and viewed toggle always stay in the DOM. Beyond 2500px from the viewport, a placeholder of the measured height replaces the column, following the same contract as Full diff. `content-visibility: auto` was rolled back after measurement because it reduces neither the DOM nor the heap and worsens p95 on top of unmounting.
