# Decision log

Decisions made during development, grouped by subsystem: what was decided and why. Implementation details live in the code. This log holds only what the code does not explain.

To maintain the log, add each new decision as a dated entry in its section. When reversing an old decision, keep its entry. Mark the new one "replaces the decision of …", and leave the old one as history. Each entry records a decision in 1 to 3 sentences: what was decided, why, and what it constrains going forward. It is not a work report. Leave out implementation progress, measurements, file lists and line numbers, which belong in the code and PR.

## Dependency management

- **2026-11-01 · External dependencies use exact versions.** Updating dependencies or pnpm requires an explicit change and the project checks. `saveExact` pins newly added packages, and internal dependencies keep `workspace:*`.
- **2026-11-01 · Dependabot proposes updates in one weekly PR, for versions at least 7 days old.** Exact pins stay, and the PR goes through the same CI as any change. The TypeScript major waits for typescript-eslint support.

## Session↔server protocol

- **2026-08-19 · Version handshake on every worker request, not just the first `next`.** The CLI stores no state between invocations, and the check costs almost nothing.
- **2026-08-19 · Version compatibility: minor releases break compatibility in 0.x, and matching major versions suffice from 1.0 onward.** The single source of truth is `protocolVersionsCompatible` in `@sherpa/protocol`.
- **2026-08-19 · `taskTypeSchema` is a strict enum.** New task types require a minor version increase. The validator rejects unknown types (fail-closed).
- **2026-08-19 · Worker endpoint paths live in `WORKER_ENDPOINTS` in `@sherpa/protocol`.** Both the server and CLI use them. They are a contract, not an implementation detail.
- **2026-08-19 · RPC error codes map to HTTP statuses through a table in `http.ts`.** unauthorized 401, bad_request 400, unknown_task 404, version_incompatible / lease_not_held / worker_conflict 409, result_too_large 413, internal 500.
- **2026-08-19 · Result limits are 256 KB in the CLI and 1 MB on the server.** The CLI rejects the result locally ("shorten the file and call `complete` again", exit code 1, task stays leased), so the model can retry. The server's `result_too_large` guards against bypassing the CLI. A body over 1 MB is rejected as `bad_request`.
- **2026-08-19 · `prKey` validation uses `prKeySchema` in the protocol.** The alphabet is `[A-Za-z0-9._-]`, and the first character must be a letter or digit. Both sides validate it: the server before creating PR state, and the CLI before inserting it into paths.
- **2026-08-19 · The PR is supplied explicitly through `SHERPA_PR` or `--pr`.** Resolving a PR from the working directory requires a host adapter, so the skill passes the PR itself.
- **2026-09-23 · `worker next` waits indefinitely for a task, and the server sets the long-poll window.** Every empty exit woke the model, and in a harness with background processes, waking it with a large context rewrote the entire prompt cache. The CLI retries at the end of the server's window and consumes `idle`. Only a task, `done` or an error reaches the caller. There is no wait field in the request or `--wait-seconds` flag. Killing the call on a harness timeout is safe because `next` is idempotent and returns the worker's live lease to that same worker. The CLI does not monitor its ancestor processes. A process that outlives a killed harness waits until a new session displaces it, at a cost of at most 1 task until its lease ends.
- **2026-09-11 · Local review publishing rounds reach the agent as queue tasks rather than through a separate channel.** Only the local host creates rounds. Other hosts have no orchestrator, and publishing still goes to the host without creating a task. The queue gives a round what a dedicated endpoint would not: it survives session restarts, is leased with retries, and joins the shared ordering as `interactive`. The reviewer is waiting on screen for fixes, so background route generation must not overtake it. The cost is a protocol minor increase from 0.11 → 0.12 under the 2026-08-19 rule. `taskTypeSchema` is strict, and a session running an old bundle must not receive an unknown type.
- **2026-09-23 · The `comment` publishing mode does not increase the protocol version.** Worker endpoints and the task schema stay the same, and UI endpoints do not check the version because the UI and server ship in one bundle. Only the English `review.feedback` instruction text changes for the new mode.
- **2026-10-10 · Host concepts remain in the protocol as host-declared properties, and comments describe them independently of any single host.** `sticky_ship`, `commentIssues`, `commentResolve`, ownership and extra lenses are capabilities a host may declare, not one host's mechanisms. Comments in `packages/protocol` and `docs/protocol.md` explain a field's general meaning and use a specific host only as an example. The protocol does not cite investigations of individual host APIs.

## Queue and worker liveness

- **2026-08-19 · A late `complete` gets no grace period.** Leases expire lazily at the start of any operation. A late worker gets `lease_not_held`, claims the same task through `next` (attempt+1), and submits its finished result immediately. No work is lost, and there is no need for a separate "accept from the previous owner" path.
- **2026-08-19 · An empty `complete` result returns `rejected`, and the task stays leased.** This is the minimum fail-closed check until result schemas exist.
- **2026-08-19 · The worker slot is 1 SQLite row per PR, and liveness is computed lazily on reads** (`lastSeenAt + WORKER_DEAD_AFTER_SECONDS > now`). The only timer fires when the worker is due to be declared dead, so "Agent disconnected" appears without incoming requests. In a pending `next`, the server rechecks slot ownership on every wakeup so an old worker cannot take a new worker's task.
- **2026-08-19 · Reconnection means a new `workerId`.** `register` always generates a fresh id. The debugging override `SHERPA_WORKER_ID` is the exception, because otherwise registration and subsequent commands would use different identities and the session would conflict with itself.
- **2026-08-19 · Session identity lives in `~/.sherpa/prs/<prKey>/worker-id`.** An environment variable does not survive separate shell calls from the harness.
- **2026-08-20 · The server writes `worker-id`, not the CLI.** With slot takeover, both parallel sessions receive a successful `register`, so CLI write order would depend on a race between network responses. The server writes the file synchronously in the registration endpoint, keeping write order aligned with slot acquisition order.
- **2026-08-19 · A displaced worker's leases return to the queue as soon as the slot is taken over.** Return semantics match expiration (attempt+1). Status: replaces the 2026-08-19 decision. Previously, leases were left to "expire on their own", which could leave an interactive task waiting for up to 10 minutes after reconnection.
- **2026-08-20 · `register` stays a separate operation and is not built into `next`.** It explicitly says "I am a new session", takes over the slot and returns the previous worker's leases. Registering on every `next` would let a zombie session take the slot back on every call. The asymmetry is deliberate: `register` takes over, and `next` from a non-owner receives "stop the loop".
- **2026-08-20 · The new session always wins.** `register` with a fresh `workerId` takes over the slot even from a live worker. The previous worker's leases return to the queue immediately, and pending polls wake up with `worker_conflict`. Status: replaces the 2026-08-19 and 2026-08-20 decisions. The rule "reject a second live worker", together with the fallback "retry registration using the id from the file", merged parallel sessions into one, with both acting as the worker. Remaining limit: a displaced session that ignores "stop the loop" can read the new id from the shared file. File-based identity does not protect against a deliberately disobedient model.
- **2026-08-20 · Worker liveness treats a disconnected connection as a strong signal and silence as a weak one.** A worker is alive if its worker connection is open, or it holds a lease and has been silent for less than `WORKER_DEAD_AFTER_SECONDS` (6 minutes), or it has been silent for less than `WORKER_GAP_GRACE_SECONDS` (60 s, the gap between loop calls). The server detects a killed idle session in 1 minute instead of 6. A killed session with a lease still takes 6 minutes because the server cannot distinguish "killed with a lease" from "working silently". The grace period is an internal server policy and is not part of the protocol.
- **2026-08-19 · Queue-change notifications use a separate channel from "work available".** The work-available channel wakes long polls, while the UI needs every mutation, including lazy expirations during reads. Notifications go out after the transaction commits and only when something actually changes.
- **2026-08-20 · The server shuts itself down when idle, with no `down` command.** It is busy while at least 1 connection is open (a UI tab or pending poll), or less than 15 minutes have passed since the last incoming request. Internal timers do not count as activity. Shutdown follows the same path as SIGTERM: the server removes the manifest and logs the reason in `server.log`. The timeout is disabled in development mode.
- **2026-08-27 · There is no "Agent disconnected" banner. The status lives in the agent indicator,** and its popover explains that "the reader remains fully functional, and marks and drafts are saved". This reverses the corresponding design handoff item.
- **2026-08-31 · `done` when the UI leaves.** The server returns `done` when the UI has connected before, has been absent for longer than `UI_GONE_GRACE_SECONDS` (60 s, since reloads, sleep and brief network interruptions break connections for seconds), and the queue has no open tasks. Closing a tab does not interrupt generation already in progress. The server never returns `done` before the UI first connects, and a returning tab restores presence. There is no machine-readable reason field because the harness behaves the same for every reason, and text is enough for the person.
- **2026-09-02 · A task cancelled while leased stays "with the worker" until its next request.** Its status becomes `cancelled`, but the holder and lease deadline remain until the worker responds, the lease expires or the worker is displaced. The UI therefore shows that the agent is still busy with the cancelled task. Generation does not count this holding state as an open task, so it does not block a new run.

## CLI and skill

- **2026-09-25 · Task waiting is handled by the prompt, without harness adapters.** Idle time must cost zero model turns. SKILL.md describes 2 branches based on harness capabilities, not names: a background call that wakes on completion (Claude Code, Cursor), or a single blocking call with an explicit 1-day tool timeout (OpenCode, pi, Codex). In Codex, this wording overrides its system rule "do not block for more than 60 s". The model writes a cell with a 1-day yield and a polling loop inside, using 0 turns over 10 minutes versus 23 without the instruction. This rules out a separate `worker codex` handler on app-server. The CLI, protocol and server do not need to know about the harness.
- **2026-09-29 · The blocking-wait branch names the cell pragma and removes the tool's documented limits.** This refines the 2026-09-25 decision. "Set all timeouts to 1 day" did not work on gpt-6-astra. The model sets 1 day for command and polling calls, but not for the cell running them, and sets 60 s on `wait` because of the Codex system rule and "effective range 250-30000" in the tool description. This produced 15 turns over 10 idle minutes, consuming 90% of the reviewers' session tokens. The skill now says explicitly: 1 day at every layer, including the `// @exec` cell directive, a polling loop inside the script, documented ranges are not a limit, and the "do not block for more than a minute" rule does not apply here. The same model now uses 0 turns while idle. The text still names no harnesses, but includes the pragma syntax because the model does not come up with it on its own.
- **2026-08-20 · The skill knows the minimum, and `sherpa up` handles all bootstrap work.** The worker model does not need architecture, requirements or protocol steps. `up --pr` finds or starts the server, registers the worker, and prints the UI link and loop instructions. SKILL.md has 2 steps: `up`, then the `next` loop. *(The steps moved into `sherpa-review guide` by the 2026-11-01 decision.)*
- **2026-08-20 · Install the skill by symlinking the package directory into the harness's skills directory** (`~/.claude/skills/sherpa`, `~/.agents/skills/sherpa`). *(The directory name was changed by the 2026-10-31 decision. Superseded by the 2026-11-01 decision on npx: the skill stub is installed with `npx skills add`.)*
- **2026-08-20 · Distribution uses a standalone skill artifact, a `node:sqlite` server and 2 bundles.** Switching to built-in `node:sqlite` removed native dependencies. The server builds into a single `sherpa-server.mjs` with embedded UI assets (read from disk in development mode through a shared static-source abstraction). The CLI remains a separate, small `sherpa.mjs` because the loop invokes it on every call and startup must be fast. The distribution is SKILL.md plus `bin/{sherpa.mjs,sherpa-server.mjs}`. No checkout or pnpm is needed at runtime, and the minimum is Node ≥ 22.13. Status: replaces the 2026-08-19 decision that required the skill to run from a repository checkout. The "2 executable bundles" layout is replaced by the 2026-10-10 decision.
- **2026-08-20 · `--harness` and `--model` are free-form display strings.** Actual values vary (`claude-opus-5[1m]`, `gpt-5`), so there is no allowlist check. The CLI trims quotes and whitespace and truncates to 64 characters, the server stores the values as received, and the UI shows "Agent · harness · model". Registration renewal updates the labels, and taking over another dead worker's slot resets them.
- **2026-08-20 · All model-readable text is English, and all reviewer-readable text is Russian.** An English SKILL.md requires English CLI output and server worker text, or the skill would refer to Russian loop phrases. The markers "stop the loop" and "DONE" form a contract between SKILL.md and the code, enforced by a test that looks for SKILL.md phrases in the built bundles *(now between the `guide` text and CLI output, per the 2026-11-01 decision)*. The UI, `server.log`, development scripts and code comments are Russian.
- **2026-09-01 · The distribution version is a single `version` field in the root `package.json`.** There were 3 unsynchronized versions (CLI, UI and a hardcoded server version), while `--version` printed a placeholder. The first numbered release is `0.2.0`, since `0.1.0` is already used in the history of the server constant. `PROTOCOL_VERSION` tracks compatibility separately and is not tied to the distribution version.
- **2026-09-10 · The server daemon starts with `--use-system-ca`.** A review host or issue service may use certificates signed by a custom CA. That CA is in the macOS system store, but Node trusts only its own bundle. In a harness without `NODE_EXTRA_CA_CERTS`, the diff failed to load with "network unavailable (fetch failed)". The CLI passes the flag when spawning if the current Node version supports it (introduced in 22.15/23.8, above the distribution's 22.13 minimum). On older runtimes, it silently omits the flag and keeps the previous behavior. `NODE_EXTRA_CA_CERTS` continues to work on top. Network errors now include `cause` (`SELF_SIGNED_CERT_IN_CHAIN`, `ECONNREFUSED`), because the log did not reveal the reason without it. The 2026-10-10 decision clarifies where the flag comes from.
- **2026-09-11 · Invoking the skill without arguments starts local review rather than reviewing the current branch's PR.** With no argument, the skill runs `up --local <current working directory>`, even when the checkout's branch has a PR. Someone invoking Sherpa in the middle of work wants to review what they have written now, including uncommitted changes. PR mode requires an explicit link, number or key. PR discovery from cwd (`pr-discovery.ts`) remains in the CLI for calls with neither `--pr` nor `--local`.
- **2026-09-23 · The CLI supplies the result-file path instead of letting the model choose it.** Models used predictable names in the shared `/tmp`, while each server had its own task numbering. Two sessions on the same machine wrote to the same file, and a failed write followed by `complete` submitted another session's result. `worker next` prints `<os.tmpdir()>/sherpa-<uid>/<prKey>/<hash of SHERPA_DIR and workerId>/<taskId>-<attempt>.<json|md>`. The path is unique to the lease, so a file there was either written during this attempt or does not exist. The CLI does not delete an existing file because a repeated `next` returns the same lease, and deleting it would erase a finished result. The CLI accepts a root in shared tmp only if the current user owns it and others cannot access it. The path is a CLI client detail, so the protocol stays the same. `complete` does not reject a different path.
- **2026-10-10 · There is one `sherpa` command, and the server is a module it loads lazily.** The distribution still has 2 files, `bin/sherpa.mjs` and `bin/sherpa-server.mjs`, but only the first is executable. The second is a module exporting `runServer`. Only the `sherpa server` subcommand loads it with `import()` at a path computed at runtime. `up` daemonizes `node <sherpa.mjs> server …`. The public distribution exposes one command, while the worker loop still loads neither the server nor UI, so the CLI must not import server code statically. The CLI composition root sets the daemon's Node flags (`--use-system-ca`), and the core only filters out flags unknown to the runtime. Replaces the layout in the 2026-08-20 decision. *(The command and file names were changed by the 2026-10-31 decision.)*
- **2026-10-10 · Checkout selection for `up --local` first tries the VCS whose marker is in the directory itself, then the first in list order that recognizes the directory.** This preserves the previous fixed VCS order without naming VCS implementations in the CLI core. The "deepest checkout root wins" rule was rejected because it queries every VCS on each call for a single case: a nested Git repository opened from somewhere other than its root.
- **2026-10-19 · Printed commands are complete: `node <path to sherpa.mjs> … --pr <key>`.** Commands without `--pr` failed to find the PR outside a checkout where the CLI could discover it. The model also added its own skill path to a bare `sherpa …`. Every command the CLI prints for the model therefore contains the absolute path to the running CLI and the key it connected to, quoted for a POSIX shell. SKILL.md instructs the model to run them as printed. Only the builders in `packages/cli/src/format.ts` assemble them. *(The start command printed by `guide` from the npx cache is `npx -y sherpa-review@<version>`, per the 2026-11-01 decision.)*
- **2026-10-31 · The public name is `sherpa-review` everywhere: GitHub repository, npm package, skill, command and distribution files.** Bare `sherpa` is taken on npm and lost on GitHub among speech recognition projects, and one name in all places removes the question of what to install and what to call. The skill is `sherpa-review` (`/sherpa-review`, `~/.claude/skills/sherpa-review`), the distribution is `bin/sherpa-review.mjs` and `bin/sherpa-review-server.mjs`, CLI messages use the `sherpa-review:` prefix. The product name Sherpa, the private `@sherpa/*` workspace scope, `~/.sherpa`, `SHERPA_*` variables and the `sherpa:` markers in GitHub review bodies stay: they are not typed by users, and changing them would orphan existing state and drafts. *(The private workspace root is `sherpa-review-monorepo`, per the 2026-11-01 decision.)*
- **2026-11-01 · The model's session guide is printed by `sherpa-review guide`, and SKILL.md is a stub.** An installed skill stays as it was copied, while the package updates, so modes, start and the loop live in the CLI, and SKILL.md only calls `guide` and tells the model to apply its output to the skill argument. The model classifies the argument from the text, the code has no classifier. Host-specific parts (which arguments belong to a host, what it needs, the local review base) come from CLI plugins (`CliHostPlugin.guide`, `detectLocal.defaultBase`), so the core names no hosts. - **2026-11-01 · Until there is an npm release, the skill is installed by building a checkout and symlinking `packages/skill/dist`.** The release script that committed the built distribution to a root `skill/` directory did not survive the move to GitHub, so no build artifact is versioned. Publishing to npm replaces this path. *(Superseded by the next decision.)*
- **2026-11-01 · The distribution is the `sherpa-review` npm package run through npx, and the skill is a stub installed with `npx skills add`.** The stub, `skills/sherpa-review/SKILL.md`, runs `npx -y sherpa-review@latest guide`, so a new session always gets the latest release and nobody updates a copied skill directory by hand. `packages/npm` (formerly `packages/skill`) builds the package: a generated manifest with the root version, one bin, no dependencies, and the same 2 files in `bin/`. `pnpm release` builds and checks it and prints `npm publish`, it publishes nothing itself. `version.json` is gone: the version is embedded at build time.
- **2026-11-01 · A session is pinned to the exact package version it started with.** npx names its cache directory by the spec string: `@latest` re-resolves the tag on every run and installs a new release into the same directory, while an exact version is found by its id without a network request and its directory never changes. ## Host adapters

- **2026-08-20 · The review contract is the `ReviewHost` interface and domain schemas in `@sherpa/protocol`.** All host IDs are opaque strings (`hostIdSchema`). `PrDiff.headCommit` is the host's reviewed side (which may be a synthetic merge commit instead of the branch HEAD). `watchThreads` promises snapshots and convergence, not reactivity. The host declares optional capabilities in `capabilities`, and the UI hides unavailable actions.
- **2026-08-21 · The host adapter is selected by `prKey`.** The key prefix names the adapter (`fixture-<medium|small|large|edge>` selects the fixture host). Without a known prefix there is no host, and only the queue works. The fixture host is a full server host. It runs UI development mode and e2e without a network.
- **2026-08-21 · Fixtures live in a separate `@sherpa/fixtures` package.** It has 2 consumers, server contract tests and the browser state gallery, so the package has no Node APIs and depends only on `@sherpa/protocol`.
- **2026-10-10 · Fixtures depict a PR in the fictional GitHub project `quillmart/quillmart`.** Fixtures contain no real host data. They use `services/orders/…` paths, ownership from `.github/CODEOWNERS` (`ownershipSource = 'CODEOWNERS'`), GitHub links to PRs, blobs, blame and issues, and fictional bots. Host properties (`sticky_ship`, `commentIssues`, ID signs) stay. Recorded responses from a real host live only alongside its adapter.
- **2026-08-20 · Threads form a tree, and comment IDs are opaque strings.** Live data has depths up to 14 and branching at ~7% of nodes. Host PR comments can have negative IDs, so code must not assume `id > 0`. The adapter computes whether an anchor is outdated and returns the result.
- **2026-08-27 · Ownership zones describe the entire PR, including zones outside the reviewer's ownership.** They are visible even to someone without a zone. A file belongs to at most one zone. `zones: null` signals reduced functionality (directory fallback or an unknown login), and the UI returns to prefix grouping.
- **2026-08-21 · The UI supplies lens labels by lens ID, with the host's label as a fallback.** The UI labels known IDs (`mine`, `pci`) itself. An unknown lens from a future host shows the host's label because the filter is extensible and must neither crash nor hide it. Status: the decision of 2026-10-10 supersedes the `pci` part. The UI labels the audit lens with the name in its `audit` field. Only `all`, `mine` and `generated` are known by ID.
- **2026-08-27 · A lens with zero files in this PR is not rendered at all**, either as a chip or as a select option. The PCI chip in the header and the audit banner use the same visibility rule. Supersedes `docs/design/SPEC-elements.md §4.2` for empty lenses.
- **2026-08-27 · The ownership lens is always visible.** Hiding lenses with zero files applies only to other lenses. With no owned files in the PR, "My files" is visible and disabled with an explanation, just as it is when there is no ownership zone.
- **2026-08-20 · The server synchronizes file viewed marks with the host in both directions.** The host may store a per-file mark keyed by content hash, which survives iterations as long as the file is unchanged. Partial progress (seen ranges) stays local.
- **2026-09-03 · "Open in external editor" is removed from the product, along with its endpoint.** PR files are not available locally, so there is nothing to open. The file link points to the host, with `hostFileUrl` alongside `blameUrl`.
- **2026-09-12 · The local review adapter is named after its VCS, `local-<vcs>`.** This is both the key prefix (`local-<vcs>-<directory>-<hash>`) and `SelectedHost.name`. Local review can use more than one VCS, and the key prefix selects the host, so plain `local` would leave no room for another VCS. The CLI flag remains `--local <path>`. The command detects the checkout in the directory itself. Status: the decision of 2026-09-21 supersedes the adapter part. There is one adapter in `hosts/local/`. `local-<vcs>` remains the key name and `SelectedHost.name`.
- **2026-09-21 · There is one local host, with the VCS behind the `LocalVcs` interface.** Tree snapshots, iteration history, threads and rounds do not depend on the version control system, so a second adapter would copy all this logic for a dozen commands. Each VCS has a backend (for example `git-vcs.ts`), with one host directory, `packages/server/src/hosts/local/`. Outside it, the VCS type is visible only in the key and host name (`local-<vcs>`, for example `local-git`).
- **2026-09-21 · The CLI detects which VCS the directory uses.** The server neither guesses the VCS type nor receives it through a flag. It reads it from the key prefix built by the CLI.
- **2026-09-21 · The default Git base is `origin/HEAD`, then `main`, then `master`.** If none of these branches exists, the command fails and asks for `--base`. Git has no single default branch, and guessing where the branch forked costs more than asking. For the same reason, `PrMeta.toBranch` is the base ref used for the diff, without a hardcoded `main`.
- **2026-09-21 · Git rename detection is disabled (`--no-renames`).** A VCS backend that does not detect moves shows a move as "old path deleted + new path added". Diffs from different backends must read the same way. The same tree must not give the reviewer different file cards depending on the VCS.
- **2026-09-21 · Git status and diff use explicit configuration overrides.** `-c core.quotePath=false`, `a/` and `b/` prefixes, no external diff or textconv. Git output is the format parsed by the snapshot, and user settings such as `diff.noprefix`, `core.quotePath` or an external diff would silently break parsing.
- **2026-09-11 · A local review key includes the project directory, branch and explicit base:** `local-<vcs>-<directory name>-<8 hex sha256(realpath + "\n" + branch + "\n" + base from `--base`)>`. Another branch in the same directory or a different base is a separate review. Its route, progress and comments describe a different diff and must not share state. The base is also part of the key because an existing server for that key is reused as is. Without it, `up --local . --base main~5` would reach a server comparing against merge-base and print a base that server does not use. The CLI names the branch (`--branch`) it used to build the key, and the branch goes into `local-host.json`. If it no longer matches, all host endpoints refuse and ask to restart `sherpa up --local <path>`, instead of silently reviewing changes from another branch.
- **2026-09-11 · The local review project directory must be explicit.** `--local` without a path is an error with guidance. The agent's cwd is not always the directory the person wants to review, and a mistake here costs an entire review of the wrong code. Invoking the skill without arguments becomes `up --local <current working directory>`. The agent makes that choice, not the CLI.
- **2026-09-11 · The local host polls the working tree every 30 s, without debouncing.** There are no file watchers. Changes come from both the editor and the agent, and inotify across the entire project directory costs more than polling. A tick is cheap. It reads checkout information, resolves the base, and checks VCS status and the mtime and size of changed files. The full diff is recomputed only when this fingerprint changes. Every tick resolves the base to a commit (merge-base with the base branch, or the ref itself for an explicit base). The base branch beneath the checkout can move, so comparison must use its current position. Otherwise a base change without tree changes would bypass the cheap check. `diffId` is the sha256 of the diff itself, so a change followed by its reversal creates no new iteration. Forced polling is exposed as `SelectedHost.refresh`. `getFileContent` calls it itself because it reads both sides from disk and must use the same iteration as the patch.
- **2026-09-12 · A local review iteration's `headCommit` is the diff fingerprint (`diffId`), without the HEAD sha.** A working tree has no head commit. Its contents identify the reviewed side. A commit in the fingerprint would also get in the way. The UI truncates it to 7 characters, which are the same across all iterations of one checkout, so the banner would read "route built for 6630996, working tree already at 6630996". Consequently, a commit that leaves the diff contents unchanged does not advance the iteration. Thread `pinnedTo.commit` and the publication round's head use the same fingerprint.
- **2026-09-12 · The local host lists previous iterations and computes a slice between them (`capabilities.iterations: true`).** Without slices, any tree edit cleared viewed marks across the entire diff. Progress carryover needs an interdiff, which the host did not provide. The adapter keeps the history in `~/.sherpa/prs/<key>/local-iterations/`. `index.json` records each iteration's files (path, change type, file fingerprint, content address), and `blobs/<sha256>` stores the new side of text files. Blobs are content-addressed, so a file unchanged between iterations is stored once. History is limited to 100 iterations, and writes remove unreferenced blobs. A slice is the union of paths from both iterations whose file fingerprints differ, with `add` (only in the new one), `delete` (only in the old one), or `modify`. A binary side or a side over the size limit is returned as `binary: true` without a patch. An iteration absent from history receives a terminal `bad_request`, just like an iteration that disappeared from a real host.
- **2026-09-12 · Local review iteration history is derived data, so its failure does not break the review.** If storage cannot be read or written, the host writes a line to `server.log` and continues with one active iteration. Diff, metadata and threads are returned as usual. A slice for previous iterations gets the same terminal refusal as an unknown iteration, and progress is not carried over. `local-review.json` still fails closed because it stores the reviewer's writing, while history can be recomputed from the tree. The index itself is read strictly. An unreadable file produces an error with its path instead of an empty history, which would let the first write erase previous iterations.
- **2026-09-12 · Iteration history stores only contents consistent with the patch.** The patch comes from one VCS diff at the start of a snapshot, while the new side is read later. A file whose mtime and size differ from those seen during the check is recorded without a blob. Otherwise one iteration could contain a patch from one state and text from another. The slice would show a changed file as unchanged and carry its viewed mark over. Without a blob, the slice returns the file without a patch, marking the whole file as affected. The next snapshot collects it again.
- **2026-09-12 · jsdiff (`diff`) builds local review slice patches instead of a custom Myers implementation.** The library is pure JS, has no native dependencies, and esbuild includes it in the same server bundle. A custom diff algorithm would add another place where the diff could diverge from what the reviewer sees, just to save one dependency. The adapter adds Git-format headers itself, with `diff --git`, sides and `@@ -a,b +c,d @@`, exactly what `splitPatchByFile` splits and the UI parser reads.
- **2026-09-11 · Local review comments live in `~/.sherpa/prs/<key>/local-review.json`.** They have no remote host. `publishBatch` clears the draft flag and records the verdict. This file is their only storage. Comments are not sent elsewhere, and the publication round reaches the agent as a task. Writes are atomic (temporary file and `rename`), with permissions 0600. If the file fails schema validation, the host refuses with the path instead of starting from scratch over someone else's text.
- **2026-09-11 · A local review verdict belongs to an iteration.** `verdicts` are returned only while the iteration on which the verdict was given is active. Once the tree changes, the review is incomplete again. A real host maintains its verdict itself. Here there is no other component to do it.
- **2026-09-11 · Local review thread staleness is determined per file, independently of the rest of the diff.** `diffId` fingerprints the entire diff, so an edit in any tree file creates a new iteration. When a thread's pin differs from the active iteration, the UI shows the outdated thread below the file header instead of on its lines, with a pinned-commit badge. An unrelated edit would therefore move all threads off their lines at once. A thread whose file remains byte-for-byte identical in the diff gets its pin moved to the active iteration and stays on its lines. It becomes outdated only when its own file changes or leaves the diff, and then keeps the pin of the iteration where it was written. The file fingerprint is the sha256 of what the reviewer sees at that path. This is the patch, the `Binary files … differ` line or bytes for a binary file, or size and mtime for a file over the size limit.
- **2026-09-29 · The host supplies the ownership source name (`ReviewHost.ownershipSource`), and all local review files belong to the reviewer's zone.** The UI does not know host names or use them to guess the "My files" label. GitHub returns `CODEOWNERS`, and the local host returns the directory's VCS diff (`git diff`). The local ownership lens includes all diff files without zones. Host ownership rules are still not reproduced locally, but the person is reviewing their own changes, so "zone unavailable" in Overview was incorrect.
- **2026-09-11 · The local host has `ownershipLens: null` and `generated: false` for all files.** Host review rules are not reproduced locally. They live on the host alongside reviewer assignment, and guessing from directories is the heuristic rejected on 2026-08-20. Local review does not need a "My files" lens because the reviewer is looking at their own directory. *(Lens superseded on 2026-09-29 with all diff files. `generated: false` remains in force.)*
- **2026-09-11 · Untracked files enter the diff through a patch synthesized by the adapter.** The VCS diff does not show them, but a reviewer needs a new file just as much as an edit. The adapter writes a `diff --git` header, `--- /dev/null` and one hunk from the contents. A null byte in the first 8 KB marks a binary file, which gets `patch: null`.
- **2026-09-11 · The VCS lists untracked files, and the adapter does not walk directories itself.** Its own directory traversal would not know the VCS ignore list. `node_modules`, `dist` and logs would enter the diff and consume the file count limit. More than 1,000 files causes a refusal with an explanation instead of a silently truncated list. A change missing from a review is worse than a review that could not start.
- **2026-09-11 · A file side larger than 2 MB is not returned:** an untracked file gets `patch: null` and `binary: true`, and `getFileContent` returns `null`. This matches the GitHub adapter's `MAX_CONTENT_BYTES`. Otherwise a 200 MB dump would be read in full on every fingerprint recalculation and make the diff endpoint's response too large to read. Such a file contributes its size and mtime to the fingerprint. An image side uses its own contract limit, `IMAGE_BLOB_MAX_BYTES`. Above that limit the side is absent because `blobId` addresses content and cannot be invented for unread bytes.
- **2026-09-11 · Publishing a local review creates a task for the agent.** Each `publishBatch` opens a round, and the round becomes a `review.feedback` task. Local comments have no remote host, and their only recipient is the agent in the same session. Verdict semantics are as follows. With `request_changes`, the agent fixes code immediately without asking again. With `ship`, comments are optional, so it applies trivial changes and replies to the rest. A round is created even for ship without any comments because the session must learn the verdict. The loop then continues on its own. Agent changes advance the iteration, the route becomes stale, the reviewer reads again and publishes the next round. Status: the decision of 2026-09-23 supersedes verdict semantics and rounds without comments. Only `comment` is published locally. "Round = task for the agent" remains in force.
- **2026-09-23 · The local host publishes only `comment`, and the agent fixes code for every comment.** There is no recipient for a verdict here. The person publishes comments specifically for the agent, and approval tells it nothing. A round is created only when at least one comment is published because without comments the agent has nothing to do. The `local-review.json` schema is not narrowed. Old ship and request_changes rounds can still be read and delivered with their previous instructions, and a stored `comment` does not enter `PrMeta.verdicts`. Supersedes the verdict semantics of the 2026-09-11 decision. Status: in force by default. With `--verdicts`, the 2026-10-05 decision applies.
- **2026-10-05 · `up --local --verdicts '<instruction>'` lets local review end with Ship or Request changes.** Approval does tell the agent "a person reviewed this, you can continue", which supports pipelines such as "on ship, commit and open a PR". The calling agent enables this mode when the user has assigned an action for a verdict. Without the flag, only Comment remains. With the flag, Comment is unavailable, and comments go through Request changes as in a PR. A verdict creates a round even without comments. The flag value holds the instruction instead of relying on agent memory. Sherpa stores it in `local-host.json` and prints it verbatim in the verdict task. The agent executes the part matching the verdict. Ship does not prohibit code changes. The instruction determines what to do on approval. The last `up` wins. An existing server confirms the applied instruction in its registration response, and the CLI refuses without confirmation instead of promising an unavailable Ship action. Limitation: approval is not checked against the tree at execution time. An edit between Ship and the task goes along with the approval.
- **2026-09-23 · GitHub allows only `comment` on your own PR.** GitHub forbids PR authors from approving or requesting changes (live API: `Review Can not approve your own pull request`), so without a mode that omits a verdict it was impossible to publish a self-review. A PR is your own when its author's login matches the token owner's login case-insensitively. A PR without an author is treated as someone else's.
- **2026-09-11 · Agent replies are ordinary thread comments with `bot: true`.** The session harness supplies the login and "Agent · <model>" display name. The UI shows them with a source chip, just like an AI review bot, without special rendering. There is no separate "round reply" channel. The reviewer reads the reply where they wrote the comment. The round result (`summary`) becomes a PR discussion by the same author instead of remaining a field in a file. The reviewer reads it in the Discussion card like any other PR comment. The agent's name follows the round's language ("Agent" in the corresponding locale).
- **2026-09-11 · An accepted round immediately rereads the working tree.** `completeRound` forces a poll. Agent edits must become an iteration immediately instead of waiting for the 30 s tick. Otherwise the reviewer would see "route is stale" half a minute after the reply.
- **2026-09-11 · A round whose task failed or was cancelled is not queued again.** SQLite stores the round-to-task binding (`feedback_tasks`) and records failure in it. Otherwise reconciliation would keep retrying the same task it cannot complete. The round remains `pending` and reaches the agent with the next publication. There is no separate "retry" button.
- **2026-09-11 · The language of round replies is fixed when the task is queued.** The language fallback order is evaluated once, the prompt explicitly names the language, and the binding stores the selected locale (`feedback_tasks.locale`). Acceptance checks the voice against the exact language requested by the task. Changing the UI language during a round cannot reject the result against another language's stop list.
- **2026-09-11 · Agent replies reach threads before the round is considered complete.** A write failure leaves the binding open, and reconciliation queues the round for the agent again. Marking a round `done` before the write would silently lose replies on a storage file failure because reconciliation does not pick up closed rounds.
- **2026-09-21 · A github.com PR key is `github-<owner>--<repository>--<number>`.** The separator is doubled because an owner's login cannot contain a double hyphen, while a repository name can. The owner comes before the first `--`, the number after the last, and the repository is everything between them. The key is used in `~/.sherpa` paths, so its alphabet stays the same (`prKeySchema`). The CLI normalizes a PR link to a key before all checks so the session uses one normalized key throughout.
- **2026-09-21 · The GitHub host uses GraphQL as its main API, with REST only for patches, merge-base and bytes.** REST does not provide thread state (resolved, outdated, multiline anchor) or viewed marks at all. A GraphQL polling tick takes one request instead of a dozen. REST retains exactly 3 things absent from GraphQL, a file's unified diff, the branches' common ancestor and raw content bytes. The cost is rate limit points. Every request includes `rateLimit`, polling runs every 15 s, and when the remaining points fall below the reserve, the client waits for the window to reset instead of retrying.
- **2026-09-21 · GitHub host drafts live in a GitHub pending review, with a PR comment draft stored as a paragraph of the review body.** GitHub has no other place for unpublished text. A pending review holds line comments and one body. Body paragraphs are marked with `<!-- sherpa:draft <n> -->`, which GitHub does not render. The marker gives a paragraph a stable ID, so deleting a neighbor does not rename the others. Markers remain in the body after submission because published paragraphs are addressed through them. Without markers, published-text editing and the publication report would lose track of what they published. Consequently, Sherpa's pending review body reads as one comment on GitHub and as a thread of paragraphs in Sherpa. A draft reply in such a thread is another paragraph. Status: supplemented by the 2026-09-22 decision about a body placeholder. The body is never left empty.
- **2026-09-21 · The GitHub host publishes with one `submitPullRequestReview`, and the adapter handles retry idempotency.** GitHub has no partial success. Submission either publishes every pending-review draft with the verdict or publishes nothing. In the latter case everything goes to `failed`, and the review remains a draft for retry. GitHub supports no retry keys in either GraphQL or REST, so `~/.sherpa/prs/<key>/github-drafts.json` stores the "buffer key → comment" map. After a network error, creation is not retried blindly. The adapter rereads the pending review and recognizes an already-created comment.
- **2026-09-21 · The GitHub host has no iterations or lenses, with `iterations: false` and `ownershipLens: null`.** GitHub has no diff set that can be listed and compared. The branch head is reviewed against merge-base, so there is one iteration, slices are rejected, and progress cannot carry over between iterations. CODEOWNERS as an ownership source is a separate decision. No structure was prepared for it in advance. Status: the lens part is superseded by the 2026-09-22 decision. The iteration part remains in force.
- **2026-09-22 · The GitHub host has `editPublished: true` and `commentResolve: false`, and reads a comment's draft status from the snapshot.** GitHub allows editing and deleting your own published text, so published-text editing moved from `updateDraft`/`deleteDraft` to `updateComment`/`deleteComment`. Draft endpoints reject published comments, as on the local host. An ID prefix does not determine which pair applies. A thread comment or review body paragraph can be either draft or published. The adapter checks the thread snapshot, at the cost of one read per write. GitHub has no per-comment issue state. The entire thread is resolved, so `Comment.resolved` is `null` for every comment, and `setCommentResolved` is not implemented. The flag is constant, and reviewer identity fails closed. If `viewer` does not respond, `getPr` fails instead of returning a header without `PrMeta.viewer` (polling and pending-review lookup can still proceed without knowing the identity). A comment that started a line discussion cannot be deleted if it has replies. `deletePullRequestReviewComment` on the root removes the discussion with other people's replies, so the adapter refuses, as the local host does.
- **2026-09-22 · The GitHub host computes ownership from the base branch's CODEOWNERS, with the last rule winning.** The file comes from the PR base (`baseRefOid`), matching GitHub's own ownership calculation. A CODEOWNERS change inside a PR does not apply to that same PR. One rule determines a file's owners, the last match (other hosts may combine owners from all matching rules). A file therefore belongs to exactly one zone, and a rule without owners removes it from all zones. Having no owner does not imply `generated` because GitHub ownership does not describe review requirements. Owner teams are expanded in a separate request with the `read:org` scope. If it fails, functionality is reduced with an explanation in `note`, and the lens stays enabled.
- **2026-09-22 · A GitHub pending review body is never empty because it contains the `<!-- sherpa:body -->` placeholder.** GitHub permanently disallows `updatePullRequestReview` for a review created without a body. This is the only place for a PR comment draft, so without the placeholder the first such draft went into the buffer and the server kept retrying. A pending review is therefore created with the placeholder. Deleting the last paragraph writes the placeholder instead of an empty string, and it is never exposed as a paragraph or comment. The final body goes through the `body` parameter of `submitPullRequestReview` itself (an empty string when there are no paragraphs). There is no separate body edit before submission. An existing unfinished review with an empty body is not repaired. Trying to add a paragraph to it asks the reviewer to submit or delete that review on GitHub.
- **2026-09-22 · The GitHub host uses `Blob.isBinary` to identify binary files instead of a statistics heuristic.** For a pure rename, REST returns exactly what it does for a binary file, no patch and zeros in `additions`/`deletions`. The "no patch and zero statistics" rule therefore showed an ordinary `.ts` file as "binary file not shown". The flag is requested from blobs in one aliased query for the entire diff, and only when files without patches exist. A missing blob or failed query gives `binary: false` because a text file without a patch is more accurate than a false binary. The cost is one extra request per diff containing such files.
- **2026-10-06 · Profile photos use `ReviewUser.avatarUrl`, which the reviewer's browser loads directly without a server proxy.** The host supplies the photo URL. GitHub gets the author's `avatarUrl` from the same GraphQL queries. All avatars are circular, with or without a photo. The bot square (radius 4 in threads, 5 in markers and the participant list) is removed. The label and `bot` chip identify a bot. If the photo fails to load, the UI draws initials as before. The schema accepts only https. The field is not passed to the model, so the protocol version does not increase.
- **2026-10-10 · Hosts connect through a plugin list in the composition root, and the core does not know them by name.** The server selects the first `HostPlugin` (key prefix and factory) whose prefix matches the key. The CLI queries `CliHostPlugin` (`normalizeKey`, `discoverPr`, `detectLocal`) in order. Each list is declared only in its package's `hosts/all.ts`, imported by entry points and tests. There is no runtime loading. The build determines which hosts are included, so a build without a host removes its plugins and their entries in the roots. The plugin contract belongs to the build, does not cross process boundaries, and lives in `server` and `cli`. The protocol retains only the host key parts shared by the CLI and server, the `local-<vcs>-` structure and the GitHub key format.
- **2026-10-10 · The fixture plugin lives in the server, and the `ReviewHost` contract suite is exported as `@sherpa/server/testkit`.** The server depends on `@sherpa/fixtures`, so putting the plugin in fixtures would create a cycle. Adapters use the contract suite through a subpath export instead of a relative path, the same way an adapter extracted into a separate package will use it.
- **2026-10-25 · `startServer` receives hosts only through the `hosts` plugin list.** A second source, a ready-made factory for tests, required an options union whose mandatory fields needed a runtime check. A test with an assembled host wraps it in a plugin with an empty prefix (`hostPluginOf`). A server without a host uses an empty list.


## Diffs and images

- **2026-08-20 · Diffs travel as raw per-file unified diff (`FileDiff.patch`), and only the UI worker parses them into a line model.** The adapter and server do not interpret patch text.
- **2026-08-22 · For context expansion, the host returns the entire file contents, and the UI computes the expansion.** An optional `ReviewHost.getFileContent(fileId)` → `{oldText, newText}` and `capabilities.fileContent` replace a context-width protocol. Context lines are identical in both versions. The UI fills gaps itself and gives the trailing gap its actual length.
- **2026-08-27 · The ±20 step belongs in gaps between hunks, and the file card header button expands the entire file.** Supersedes `docs/design/SPEC-elements.md §2.13` for the ±20 button.
- **2026-08-28 · Loaded context is not persisted.** Expanded gaps live in tab memory. Context provides a view around changes rather than review progress, and does not change file read status.
- **2026-09-04 · Image blobs are content-addressed, and the server determines their type.** `ReviewHost.getBlob(blobId)` and both sides of `FileDiff.image` use `{blobId, size}`. The server caches bytes as files in `~/.sherpa/prs/<pr>/blobs/` (no SQL query needs them). The UI refuses to load a side larger than `IMAGE_BLOB_MAX_BYTES` (10 MB) before making a request. `Content-Type` comes from magic bytes, not the extension or host header (a host may return svg as `text/plain`). Unrecognized content gets `application/octet-stream` with `nosniff`. The server recognizes images by extension because the change list marks png as non-binary. An svg exists both as an image and as a text patch. In comparison mode, the UI fills changed pixels with the accent colour and unchanged pixels with a desaturated new frame. Different sizes are aligned in a shared rectangle from the top-left corner.

- **2026-09-12 · The path in the file card header truncates from the left using the tree's technique: `direction: rtl` on the container, with the content in `bdi`**. `unicode-bidi: plaintext` does not work because it takes the direction from the first strong character. For a path that is LTR, so the ellipsis ends up on the right. The filename does not shrink while there is still a path beside it.
- **2026-09-11 · Syntax highlighting uses highlight.js through `lowlight` instead of a custom lexer.** The custom line-by-line lexer knew seven languages, and each new language would need its own grammar. The registry is now `packages/ui/src/diff/languages.ts` (the `common` set plus languages common in monorepos: proto, Dockerfile, CMake, Scala, Groovy, Dart). The four categories from `docs/design/README.md` §1 remain. A table maps hljs scopes to `keyword/string/comment/decorator`, and everything else is plain. Each side of a hunk is highlighted separately. The old (`del` + context) and new (`add` + context) versions are assembled into two texts and highlighted as a whole. Multiline comments and template strings now render correctly, and a mixture of two file versions is no longer treated as code. The cost: parsing the `huge` fixture in the worker rose from 49 to 268 ms for all 100 files, and the UI bundle grew by 368 KB raw (the registry is in both the main chunk and the worker chunk). Remaining work: load grammars lazily and deduplicate the registry across chunks. Context expansion highlights only the expanded part, not the entire blob.
- **2026-09-18 · A Markdown file renders as a document in segments of consecutive lines, without joining across gaps.** Joining adjacent fragments would change the meaning of the markup. Full context can be expanded in code mode. It uses the same parser as comments (the `comment` profile), raw HTML stays text, and YFM extensions are not supported.
- **2026-09-18 · A document anchor refers to lines and is shared with code mode.** A comment, note or question from the document attaches to source lines on the same side. Switching views does not create copies. The exact quote lives only in the question anchor (`selectedText`, up to 4000 characters). It is not included in the link or the comment.
- **2026-09-23 · Markdown/Code mode is stored per file in the diff store instead of the card state.** Full diff virtualization and the stop column unmount cards, so local state used to reset to "Code" on return. The mode does not survive a page reload, just like expanded context.
- **2026-09-23 · The hunk's entity name is removed from the card header and the outline.** The heuristic based on text after the second `@@` and declaration regexes produced garbage (`import {`, a random README line) and labelled the whole file with the first hunk's entity. The outline for a single-file PR labels hunks by line range. It does not try to infer function or class names mechanically.
- **2026-09-23 · The line-number column width follows the digit count of the largest visible number, with one width per card.** The card calculates the digit count from the model after context expansion and route slicing and passes it through a CSS variable. In split mode both halves share the width. Space for 4 digits is not reserved in advance, so short files do not lose room. The minimum is 2 digits. All line-number columns have the same width. In unified mode the old numbers leave room on the left for the thread marker at the card edge, otherwise it covers the number and the expansion target.
- **2026-09-23 · All files in the UI follow tree order. Host order is ignored.** The diff is sorted at the entry point (`fetchReviewDiff`), with directories before files at each level and both groups in alphabetical order. The tree, full diff cards, navigation keys, palette and "Other" follow the same order. Route anchors still determine the order of files within a stop.

## Route

- **2026-08-25 · The route snapshot contains only model output. The UI calculates derived data.** The snapshot contains the plan (id, number, tier, title), stop content (paragraph, bridge, anchors, test digest, dropped assertions, validator notes), summary, traversal order and provenance. The UI derives file chips, counters, coverage fractions and the contents of "Other" from anchors and its own diff model. The snapshot has no derived fields, so they cannot drift out of sync. The model places anchors by file path, and the validator converts them to `fileId`.
- **2026-08-25 · "Other" is a synthetic stop added by the server when it accepts the skeleton** (the last plan number, with "ready" status). The UI hides it when there are no uncovered lines. Promoting it above a 40% share changes the render order, while numbers stay fixed by the plan. Status: the visibility rule is extended by the decision of 2026-09-23.
- **2026-08-25 · Generation phases are `none/reading/filling/ready/failed`. The summary arrives in full with the skeleton.** There is no token streaming in the polling loop, so the handoff's promised "streaming Summary" becomes a placeholder until it is ready. A section failure is the status of its stop, not a phase. "The agent died during generation" is not a phase either. The UI combines `filling` with worker status. Route text is in Russian because the reviewer reads it, and prompts are in English.
- **2026-08-26 · A section failure does not fail the route.** The `failed` phase applies only to the skeleton. A failed section gives its stops `failed` status with a note, and the route reaches `ready` with unfilled slots. Cancelling the skeleton from the UI sets the phase to `none`, meaning "stopped", not "broken". `contentHash` is calculated from model content without service fields, so the same route from different sessions produces the same hash.
- **2026-08-26 · Generative results go through a synchronous acceptor inside the `complete` transaction.** A cache in the orchestrator separates asynchronous diff reads from acceptance. Accepted results are applied through a callback after commit, with no nested transactions. Rejection does not consume an attempt or release the lease. The budget is 3 rejections per lease, after which the task becomes `failed` with the last raw output. A third outcome, "nothing to validate against" (the diff is still loading after a restart), does not consume the budget.
- **2026-08-26 · The orchestrator is a reconciliation-driven state machine, not an event-driven one.** On every queue change, it recalculates stop statuses and phase transitions from queue state. The same code handles server restarts, agent death and session displacement without special branches. Skeleton rescheduling is limited to three tasks. Sections are queued in plan order and accepted in arrival order without buffering. The first result submitted wins a range conflict.
- **2026-08-26 · Generation context is passed as files, with line numbers in the patch gutter.** The task carries a short pointer (less than 500 bytes) and paths to the guide, PR context and result schema. The same traversal that the validator later uses to accept anchors adds line numbers for both sides to the patches. Printed and validated numbers match by construction, so the model does not count lines from the hunk header. The context budget is 320 KB. The full changed-file list is never truncated (the coverage rule). Patches are truncated, generated ones first, then the largest ones, with test files last in section context. Status: the truncation order and treatment of truncated patches are superseded by the decision of 2026-10-19.
- **2026-09-02 · The server writes context shared across tasks to disk once, under `payload/shared/`,** keyed by its content. The rule "read files under `shared/` once per session" lives in SKILL.md and task instructions. Previously, five questions about one PR meant reading the same diff five times, at up to 80k tokens each. Tasks remain self-contained. The file is on disk, the path is in the task, and a new session reads it as usual.
- **2026-10-19 · A patch that does not fit the shared PR diff budget goes into a separate file with the same gutter.** Previously, such a patch became a `patch omitted` note. The model could not anchor to it, so its lines ended up in "Other". Source files were also truncated before tests. The placeholder in the diff now gives the absolute path to the separate file, and anchors based on its gutter are valid. The skeleton does not need these patches because it plans from the file list and the remaining patches. A section reads only the separate files for its own stops. Truncation follows the order "generated files, tests, source files", because the plan is built from source files, while a test moved to a separate file still supports anchors. Moving patches out does not change the task's `contextFiles` or the generation cap. A generated non-test file, a file larger than the budget and an inter-iteration slice still become a note without a file. If even the placeholders exceed the budget, the smallest separate patches fall back to notes. The shared file's size limit takes priority over separate files. Filenames include the print-format version so an updated server cannot pick up the old format. Status: supersedes the part of the 2026-08-26 decision about truncation order and treatment of truncated patches.
- **2026-08-26 · Section batch size stays at one because progressive delivery matters more than latency.** Measurement on a real PR: 403 s from queuing the skeleton to completion. One task for all sections takes 294 s (−27%), but everything arrives at once. The "≤ 90 s" budget is unreachable with the current generation of models. The skeleton alone takes 77–97 s.
- **2026-08-31 · The voice validator rejects only clear violations:** emoji and six filler phrases in reviewer-facing text. Superlatives are not on the stop list because they cannot be distinguished without morphology, and a false positive wastes a model attempt on a style complaint. Subjective style rules stay in the guide. The worker is told directly: the server validates the schema, do not validate it yourself, always submit.
- **2026-08-26 · Changed whitespace-only lines do not need route coverage.** Empty separators between blocks belonging to different stops regularly appeared as "not placed". A changed line containing only whitespace and not covered by an anchor is excluded from coverage statistics entirely. It appears in neither "Other", the hatch nor the percentage denominator. An anchored line counts as before. The server and UI use the same rule, so their numbers match by construction.
- **2026-08-26 · The route in Full diff is a lightweight "file → stops" map that needs no patch parsing,** so badges appear immediately. This layer renders only in the `ready` phase. During `filling`, "not placed" cannot be distinguished from "not filled yet", so the numbers would be wrong. The same helpers calculate uncovered ranges for "Other" and the coverage bar. A file in multiple stops gets the badge of the first stop in plan order and "+N".
- **2026-08-26 · The UI does not revalidate raw skeleton output.** The handoff hint "fix the anchors and revalidate" does not apply. The `failed` phase occurs only for the skeleton, and its output schema has no anchors, so there is nothing to fix. The UI shows raw output as is.
- **2026-08-27 · The digest hides only test files belonging to its stop.** Assertion anchors pointing to files outside the stop are valid input, so the server stays unchanged. If there is no overlap, the toggle is omitted entirely. A link row says "test code is in stop NN" or "in Other" instead. If there is nowhere to link to, there is no row.
- **2026-08-31 · Filling a single stop uses the regular `filling` phase.** The endpoint queues the stop, and existing reconciliation handles the rest. Full regeneration is unavailable during this time because filling is brief, and the banner explains the state. The snapshot identifier in the request body prevents a race with snapshot replacement, because stop ids are not stable across snapshots.
- **2026-08-31 · Regeneration is available from `ready`.** The "worth regenerating" banner must offer an action. Regeneration leaves everything intact until a new skeleton is accepted. The old snapshot stays visible and readable during `reading`/`filling`. Progress is cleared and the snapshot replaced in one transaction at acceptance. Cancellation and failure restore the old route as it was. Status: supersedes the decision of 2026-08-26 under which `generate` from `ready` responded "already in progress".
- **2026-09-02 · The small-PR threshold counts only lines:** additions plus deletions ≤ 40. The "or files ≤ 1" condition is removed because it left every single-file PR without a route, even one with five hundred lines. The invariant is in `docs/architecture.md §7.6`.
- **2026-09-04 · The server deterministically recalculates the generation cap when accepting the skeleton** and stores it in the PR database. It is not carried in a task or lost on restart. Conflicted files are excluded from the route model on input, otherwise the sum of coverage-bar segments would disagree with the denominator.
- **2026-09-09 · Context expansion in a stop slice skips changed lines belonging to other stops.** Expansion used to stop at the first changed line of another stop. For a gap starting with such a line, the ↑/↓ targets appeared but did nothing, while the counter promised unchanged lines beyond it. The ±20 step now counts only unchanged lines. Changed lines belonging to other stops stay hidden in a separate gap labelled "N changed lines in other stops", just as in full-file expansion. A single slice gap can now split into several gaps with one expansion key. The remainder for that key (both unchanged lines and changed lines from other stops) is summed across all pieces, and the row's React key also includes the piece boundaries. A related dead click is fixed in the same place. When a slice merges with a real bridge in the model and hides only changed lines from other stops, the bridge gets the key, because there was nothing to expand under the slice key.
- **2026-09-12 · In a stop's file chip, the filename gets width first. Directories truncate from the left down to zero. Counters and the read checkbox do not shrink**. The "filename, then directories" order is deliberate. In a narrow column, filenames line up and the list can be scanned visually. The tooltip shows the full path.
- **2026-09-04 · Filled stops do not show validator notes.** Seven lines of "anchor dropped: nothing changed in this range" took up card space, while the reviewer cannot move an anchor anyway. Missing coverage is visible in the bar and in "Other". Notes still go into the snapshot as a generation audit trail, but render only on an unfilled stop, where they explain the empty slot. This deliberately departs from `docs/design/SPEC-elements.md §4.3`.
- **2026-08-26 · Local decisions for generative states:** "Other" counts as a ready slot in "N of M ready" (it can indeed be read). A small PR redirects to Full diff once, and only before a view is explicitly selected. Promotion of "Other" and the "worth regenerating" banner stay hidden during `filling`, because uncovered ranges in an unfinished route are empty plan slots, not a verdict on the model. The agent indicator treats any open task as work. The summary renders as plain text, without a Markdown renderer of its own. Status: the part about "Other" in the "N of M" count is superseded by the decision of 2026-09-23.
- **2026-09-23 · The reviewer sees "Other" only when the route is complete and has uncovered lines or conflicted files.** One rule (`otherStopVisible`) controls the route column, counters, Overview, palette, full diff margins and tour. A failed section counts as complete. "Other" is absent while the route is building. Previously, it flashed and counted towards "N stops" even on routes where the model had placed everything. App calculates uncovered ranges itself by parsing the diff in the background on the same worker as the view, so Overview does not have to wait for the route to open. While parsing is in progress, Overview does not show a stop count.
- **2026-10-19 · Before regeneration, an iteration change determines whether a push happened, regardless of whether a slice is available.** A slice may be unavailable (host failure or no host), and the task used to tell the model "same commit" even though the code had changed. Regeneration now has three cases: the same iteration, a push with a slice and a push without a slice. In the last case, the model receives the commits of the previous route and the current diff and compares them itself. It is explicitly forbidden to write `changeReason`, because the server would discard it without a slice anyway. A restart during plan scheduling rebuilds context through the host, including the slice and threads, instead of using the cache. Otherwise a push during downtime would always arrive without a slice, and the discussion would be lost.

## Reading progress

- **2026-08-22 · Progress records represent only explicit actions. The UI interprets defaults.** A file record appears after a reviewer action. An absent record means the default calculated by the UI (generated files count as viewed). The server does not interpret patches. The record is mirrored to the host after the local write, without guarantees. A mirror failure neither rolls back the record nor counts as an endpoint error.
- **2026-08-31 · Viewed state has three values: `true | false | null`.** `null` means "the reviewer has made no decision, and the record exists for its ranges". An explicit clearing of the mark and a synthetic record for a file with only stop ranges used to look the same on the wire. As a result, marking a stop that touched a generated file removed its default. The UI heuristic "`false` with nonempty ranges does not mean clearing the mark" was rejected because it loses an explicit clearing in the sequence "clear the mark, then mark the stop". Clarifies the decision of 2026-08-22.
- **2026-08-26 · For stop progress, the UI calculates ranges and the server stores them against the stop.** The stop mark and its files' seen ranges are written in one transaction. The server does not interpret ranges because it has no diff model of its own. Clearing a mark removes only that stop's ranges. Other stops and manual file marks stay unchanged. New route generation clears stop progress and its ranges, while file marks survive.
- **2026-08-31 · A file becoming viewed through coverage is mirrored to the host.** The UI sends deltas after recalculating ranges, without a local record or a new revision. The first snapshot is the baseline, so opening a tab does not replay history. The generated-file default, partial progress and explicit file marks are not duplicated. Status: supersedes part of the decision of 2026-08-26. "Stop marks are not mirrored to the host" still holds for the stop record itself.
- **2026-08-26 · The "show test code" toggle writes no progress, while marking a digest stop also marks its test files.** Reading without a mark is not tracked at all. The digest stop's anchors are the test files themselves, and their assertions are the contract. Otherwise "the diff you actually saw, 100%" cannot be reached in the intended flow, because test code is hidden by default.
- **2026-08-27 · A stop is marked automatically when coverage changes from "uncovered → covered".** The first calculated snapshot is the baseline, so loading server progress on opening does not look like a reviewer action. Clearing a mark by hand blocks automatic marking until coverage is lost and restored, otherwise automatic marking would immediately undo the clearing. The server handles the symmetry "clearing a file also clears its stops". Only the server knows the "stop → ranges" relation, so this also works from Full diff.
- **2026-08-27 · A stop with an unparsed file or a file whose parsing failed cannot be marked:** the toggle is disabled, a tooltip gives the reason, and a button retries parsing. The option "allow the mark but leave the failed file uncoloured" was rejected because ranges are written once when the mark is set, so the file would stay unread forever. The cost: stops cannot be marked when the diff worker is dead, which is more honest than silently losing progress.
- **2026-08-27 · Progress revisions are checked for inequality, not treated as monotonic.** They are monotonic only within one server lifetime, which is why the progress snapshot stopped being reread after a restart.
- **2026-08-27 · Marking a stop collapses it and scrolls to the next entry in the current preset**. Scrolling follows collapse, not a stepper. The last stop does not request scrolling. Clearing a file mark clears its stop mark too, for symmetry.
- **2026-09-02 · The same rule extends to files.** Marking the file the reviewer is reading scrolls to the next file in the current order and filter. It chooses the nearest expanded file below, or simply the next file if everything below is collapsed. The target's collapsed state stays unchanged. Clearing marks and noninteractive changes (server events, progress rereads, coverage from stops) do not request navigation. Only the reviewer action handler queues it. Continues the decision of 2026-08-27.
- **2026-09-12 · Progress is read for the displayed iteration, and the endpoint response identifies that iteration itself.** The tab requests progress with the displayed diff's `diffId` instead of omitting the parameter. In the stale window (a push has arrived, but the route has not been rebuilt), it shows the snapshot iteration's diff, while active-iteration progress addresses different `fileId` values. All marks on screen used to disappear. `uiReviewProgressResponse` now includes `diffId`, identifying the iteration the response was read from, not echoing the request. The UI does not apply a response for another iteration. An explicitly named active iteration uses the same path as a request without the parameter, otherwise the current snapshot's stop marks would not be found after reloading in the stale state. "Active" here means a match with the iteration named by the feed. A host that supports iterations but whose list has not arrived names no active iteration, so the requested iteration is read as is. There is one exception: a server with no iterations at all (no host, or a host without iteration support). Its single iteration is internally named `unknown`, and the response uses the name the tab gave it. This is a UI endpoint, so `PROTOCOL_VERSION` does not increase.
- **2026-09-12 · A mark is written to the iteration whose `fileId` values the UI sent, and repeated on the active iteration.** Writes previously always went to the active iteration, so a mark made in the stale window disappeared when progress for the displayed iteration was reread. There are two candidates for the marked iteration: the active iteration and the current snapshot's iteration. A tab with marks enabled cannot show any others. The mark is repeated on the active iteration only for a file untouched by the slice (read from the cache without a host request). Carryover for the pair runs once and has already happened by this point, and the reviewer has not seen a changed file. The same rule applies to a stop mark. Its ranges are stored under the displayed iteration and repeated on the active one for the same untouched files. Otherwise a route rebuild would read active-iteration progress, find no ranges and return the stop to unviewed. Clearing a mark sends no ranges, so the request cannot reveal which iteration the tab displayed. Both are cleared. Clarifies the progress carryover decision of 2026-09-02.
- **2026-09-22 · Marking a file in a stop card writes only that card's lines.** Ranges are stored against the stop (the `reviewStopFileViewed` endpoint), without pinning the file. The toggle, checkbox and card collapse state are calculated from coverage of its lines. Otherwise a file shared by several stops became fully viewed after marking one piece. A pin (manual, host or generated) can only be removed from the card in full. Clarifies the decision of 2026-08-26.
- **2026-09-23 · All progress marks go to the server through one queue, in click order.** The file, stop and card endpoints affect overlapping ranges on the server, and per-key queues would require analysing those overlaps. Clicks are rare, so a shared queue costs almost nothing. The cost is that a mark waits for the previous response, even for another file.

## Comments and publishing

- **2026-08-24 · Thread writes use REST endpoints over the host's write methods, with state converging through events.** Saving a draft returns the created comment (the composer needs its id for editing and deletion). The other endpoints return an acknowledgement without data. A successful write increments the thread revision. The UI gets the source of truth by rereading the endpoint and uses optimistic state until then. An extra read when polling detects the same write is cheaper than teaching the feed to distinguish its own writes from someone else's.
- **2026-08-25 · Publishing uses one endpoint over `publishBatch` and returns its result unchanged.** There is no progress stream. A batch has only a handful of comments, and publishing makes one host call. Any failure means the verdict is treated as not applied. The review is unfinished, and the UI offers a retry. The "Review complete" screen is tab state after successful publication, with no server persistence. After a reload, the host's PR status is the source of truth.
- **2026-08-31 · Drafts are saved only explicitly.** Typing changes composer state. The button or ⌘⏎ starts the write. After saving, the input closes and the draft stays as a card. Editing it again requires an explicit action. The browser shows its standard confirmation when leaving a page with unsaved text. Text is not written to `localStorage`. This cancels autosave from `docs/design/SPEC-elements.md §2.17`.
- **2026-09-03 · The draft buffer stores composer state instead of a phantom comment, with `clientKey` making retries safe.** A buffered record is text in an open composer at its anchor, with the status "we'll save it when the connection returns". It does not enter the thread store, polling does not remove it, slices have no phantom comments, and reloading opens the composer on the same line. The UI sends `clientKey` with every write. The server overwrites the previous record by that key and calls the host with the same idempotency key. The delivery process retries after 10/30/60 s. Buffered records count as drafts and block publishing. Status: replaces the 2026-08-24 decision under which the first save was not idempotent and the composer warned "retrying may create a duplicate" instead of retrying automatically.
- **2026-08-28 · The composer uses an existing ProseMirror editor instead of a custom contentEditable.** Guaranteed markdown round trips matter more than another custom subsystem. "Visual" is real input, not a preview, and losing `**`, backticks, lists or links would lose the reviewer's text. The dependencies are `prosemirror-{model,state,view,keymap,history,commands}` and `prosemirror-markdown`: MIT, no postinstall scripts, no React binding needed. The editor loads as a lazy chunk (325 KB, 115 KB gzipped) because the composer opens rarely and the UI bundle is embedded in the server. The store's source of truth is markdown. Other people's content keeps its own safe renderer. Two markdown stacks side by side are a deliberate cost.
- **2026-08-31 · Literal markdown is parsed on paste and when an inline marker closes.** Clipboard text goes through the same parser as switching editor modes. `**x**`, `*x*` and `` `x` `` become formatting after the closing marker. The rules do not run inside code.
- **2026-09-02 · Block input rules turn `- `, `* ` and `+ ` into list items, `1. ` into a numbered item, and triple backticks into a code block.** Backspace immediately after a rule fires restores the literal text. Enter in an empty item exits the list. Tab and Shift-Tab nest and lift an item. This adds `prosemirror-schema-list` because the base command set knows nothing about lists, and implementing item splitting and lifting by hand would rewrite the canonical module. Input rules do not create headings or blockquotes. There are no buttons or styles for them, so the resulting block would have no visible representation or way to remove it.
- **2026-08-28 · Each line has one pencil icon and no action bar in the gutter.** This cancels `docs/design/SPEC-elements.md §2.14`. Neither the contract nor host adapters support reactions, and "copy link" was removed from the file card header in the same change. Restoring the bar requires a design request and an extension to `ReviewHost`.
- **2026-08-31 · A comment's issue status is a boolean in the draft, defaulting to "open an issue".** It is not an enum of host statuses. `resolved` and `dropped` are thread lifecycle states managed by a separate method. The control appears only in new-thread and PR-level composers. Replies have no control and do not send the field. A host without `capabilities.commentIssues` has no control, which is reduced functionality rather than an error.
- **2026-09-01 · `Comment.issue` travels with the comment, and `null` means only "the host does not distinguish issues".** Without the field, the UI could not determine the toggle's state when editing the reviewer's own draft. A live PR confirmed that the host does not store `not_issue` at all, so no status means "not an issue". Where issues exist, "unknown" is not representable. The host contract suite enforces this invariant. A mismatch between the mock and the live API let the bug through.
- **2026-08-31 · The "Comments on the PR" modal contains human PR-level threads, not everything outside the diff.** PR-level means no anchor. The list includes those threads' root comments, both published comments and the reviewer's own drafts. Replies do not expand in the modal. Bot threads and threads anchored to files that disappeared stay in the Overview's "Discussion" card. They must not be duplicated as a wall of text in the modal.
- **2026-09-04 · The "Discussion" card also shows human PR-level threads.** The modal remains where reviewers write them, and the card is where they see them. Clicking a participant sets an author lens for threads in Full diff (tab memory). Overview does not navigate to a specific thread. Participants sort by open-thread count, with bots after people. Status: replaces part of the 2026-08-31 decision.
- **2026-09-01 · "Turn into a comment draft" on a note opens a prefilled composer instead of saving a draft:** nothing goes to the host until an explicit save. The initial text is the line "Quoted from the agent's answer:", a blank line, and the note text as a blockquote. The attribution is editable as ordinary text. The draft anchor covers the note's entire range.
- **2026-09-04 · An image comment has a file anchor without a line.** The "Comment on the file" item appears only in image card menus. The composer distinguishes PR, file and range levels.
- **2026-08-27 · Sticky ship is published as the host's normal sticky ship.** The handoff's promise to revoke it based on ownership zone is not implemented because there is no mechanism for it.
- **2026-09-23 · Publishing without a verdict uses `comment` mode, and `capabilities.publishVerdicts` lists available modes instead of the `stickyShip` flag.** An ordinary review that leaves comments without approving or blocking was unavailable on every host. A list replaces flags because availability depends on the PR (the host's PR settings, or the PR author on GitHub). The UI renders exactly that list without distinguishing hosts, and the host rejects a verdict outside it. ~~`comment` is always in the list~~ *(superseded on 2026-09-29: the host decides the list's contents, including `comment`, and the protocol does not require it)*. `comment` is not a reviewer verdict and does not enter `PrMeta.verdicts`. This replaces "no Publish button" in `docs/design/SPEC-additions-2026-08-26.md`: ~~the button exists and becomes the primary action when no other modes are available.~~ *(Superseded on 2026-09-24: publishing without a verdict is Comment mode in the Ship menu.)*
- **2026-09-23 · `comment` without drafts does nothing.** The response is `{[], [], true}`, and nothing is written to the host because there is nothing to publish or apply. On GitHub, a review without text and with a `COMMENT` event would become an empty PR comment. The UI keeps the button disabled and shows the reason.
- **2026-09-24 · Comment is the third mode in the Ship menu instead of a separate button.** Publishing without a verdict is a way to finish the review alongside Ship and Sticky ship. The menu choice is remembered in `shipMode` like the other modes. When only one mode is available (local review or the reviewer's own GitHub PR), the split button becomes a single "Comment · N" button without a caret. Request changes remains a separate button.

On a local host, nothing is published, and drafts go to the agent. There is one "PR or agent" choice (`draftDestinationOf`), used by the draft counter, the consequence of Comment, the PR comments modal and the result screen. Status: the source was superseded by the 2026-10-10 decision. The choice is now the host description's `drafts` field.
- **2026-09-03 · "Someone shipped first" comes from the overall PR status and the reviewers list in metadata,** both of which fit in the same cheap poll. The banner appears when someone else's ship is observed. Its time starts at observation because the API has no timestamp. Unresolved threads do not block publishing. They only appear in the summary. Drafts do block it.
- **2026-09-23 · The publishing panel is absent while review data loads.** The placeholder rendered Request changes and Ship for every host, but publishing modes are known only from the PR header. On the local host and the reviewer's own GitHub PR, the buttons flashed before a single "Publish" button replaced them. Diff loading errors already appear in the views and need no duplicate in the panel. Until the panel appears, the "ship" tour step shows a card without a ring.

## Chat and notes

- **2026-09-01 · The chat data unit is an exchange (one record for a question and answer), not a sequence of messages with roles.** Status (`queued/running/done/failed/cancelled`) lives in one place. An "answer without a question" is not representable, and cancellation and retry address one entity. The UI expands the exchange into the chat timeline.
- **2026-09-01 · An answer arrives in full when one task completes, as markdown without a schema.** The polling loop has no token streaming, so the streaming promised by the spec becomes an answer indicator and progress lines. Only structured tasks have a result schema. The shared 256 KB limit applies. The voice validator also checks chat answers because the reviewer reads them.
- **2026-09-01 · The server creates a note in the answer-acceptance transaction, with a copy of the answer as its text.** A note is self-contained and lives and is deleted independently of history. The link is one-way through the exchange id, and the "pinned" mark is derived and clears itself. The anchor carries a path alongside `fileId`, so the chip label survives the file leaving the diff. Collapsed note state stays in tab memory without persistence.
- **2026-09-01 · Cancellation works for both queued and leased tasks.** The worker learns about it on its next CLI call. Retry queues a new task for the same exchange.
- **2026-09-01 · "Ask the agent to place them" puts a question in the composer for the reviewer to send.** All entry points only prefill text. A question has one anchor. "Other" goes without an anchor and lists ranges in the text (the first 20 and "and N more"). A hatched bar sends an anchor for its own range. The button does not change the route: "the answer will arrive in chat, and the route will not change".
- **2026-09-01 · Generation, regeneration and filling remain available when the agent is disconnected:** the queue is durable, and tasks will wait for the worker. Only chat entry points lose functionality. The reader is always available.
- **2026-09-23 · Selecting text in a document does not prefill a question in the composer.** The template "What does the selected fragment mean?" existed only for Markdown and got in the way of asking a different question. - **2026-10-10 · The selection popover closes only when the reviewer scrolls, not when layout changes.** "Scroll beyond 200px" (SPEC-elements §2.15) is measured from a point recorded at the current scroll-area size. If the size changes (the chat panel opens, or the window changes), the point is recorded again. Otherwise "Ask the agent" closed its own popover because the panel narrows the diff column and moves the lines, so the "asked" chip never appeared.

## Iterations

- **2026-09-02 · The unit of time is a host iteration, with a separate `watchIterations` subscription returning the full list on change.** Threads and iterations have different consumers, so this does not extend `watchThreads`. The adapter does not return "gone" status. The server assigns it by comparing the host list with its own storage. `capabilities.iterations` means "the host lists previous iterations and returns a slice between them".
- **2026-09-02 · The tab's selected view is a client choice in the URL fragment.** Endpoints take an iteration or slice as parameters. The server has no "being viewed" state. The UI derives read-only mode from "selected iteration ≠ active iteration". `getDiff` accepts only a complete slice `{base, head}`, with no more half-specified requests.
- **2026-09-02 · "New / changed" classification uses section anchors (already converted to `fileId`), and marks carry over when the snapshot freezes.** The skeleton has no anchors, so earlier classification has no data to use. Until freezing, "N of M carried over" stays hidden to avoid a false "0 of 7" on the second pass. The model writes the reason for a change, and the server assigns its kind. Other values are discarded with a note.
- **2026-09-02 · Stale-route state is computed by a separate feed at the read boundary instead of being stored.** The route revision for the UI is the sum of the storage and feed revisions. Affected stops arrive in a second notification after the interdiff. The generation diff is tied to the task's iteration. A push during generation does not move it.
- **2026-09-02 · Progress carries over between iterations once per "source → destination" pair,** and this is recorded so a mark cleared after carryover does not return. A file's "viewed" mark carries over only for unchanged files. Explicit clearing always carries over. A force-push loses progress from a vanished iteration because the host cannot compute a slice against it.
- **2026-09-03 · The carryover source is found through progress records instead of the iteration list.** Only iterations that were active on recent versions have a list entry, so older progress was silently lost. The "`fileId` → path" map no longer depends on a stored patch because progress records store the path themselves. If neither the host, patch nor snapshot knows the source base, the active iteration's base is not substituted. A conservative mode treats the old side as affected because substitution silently produced an incorrect line map.
- **2026-09-03 · Host failures on a slice have the same classification for notes, progress and affected stops.** A vanished iteration or the host's `bad_request` is permanent. The source is marked as rejected, notes mark their anchor as lost while retaining the original, and progress moves to the next source. Everything else is temporary, with a retry after 30 s. Progress does not move to an older source on a temporary failure because a network failure must not silently downgrade the source.
- **2026-09-03 · The tab's diff follows the route snapshot.** While the snapshot describes a previous iteration, the tab stays on its diff (anchors address files by their iteration's `fileId`) and moves to the new one when a new skeleton is accepted. Previously, after a push the tab kept the old iteration's files while the route arrived with the new iteration's anchors.
- **2026-09-04 · The second-pass banner reports two things separately:** how many stops remain viewed and how many changed. The denominator includes only stops with anchors, excluding the synthetic "Other". When nothing carries over, the server gives one of three reasons: the source had no marks, marks existed but covered no complete stop, or the host did not return a slice. Counting carried-over destination lines cannot work because regeneration within the same iteration has no line carryover, which always produced "there were no marks".
- **2026-09-03 · A snapshot of an iteration lost to a force-push stays current, with editing enabled, for as long as it is the current snapshot.** "The commit is no longer in the PR" and the editing restriction appear after rebuilding for a new iteration.
- **2026-09-12 · The picker puts the active iteration first, followed by one chronology.** Snapshots no longer have a separate section at the top. The reviewer looks for an iteration, not whether it has a route, and an active iteration without a route used to appear third after old snapshots. Each snapshot sits beside its iteration. Slices keep a separate section at the end. Short row identifiers are distinguishable within the menu. They use seven characters as elsewhere, extended on collision until distinct. A shared long prefix (local review iterations recorded with the old `<sha HEAD>+<8 hex>` formula differ only in the suffix) is displayed with its start and end separated by an ellipsis. When the entire commit matches and cannot distinguish rows, timestamps are exact instead of rounded. This also applies to iterations without a route, which previously showed no time at all. Status: the separate slice section was superseded by the 2026-10-03 decision.
- **2026-09-12 · In local review, a vanished iteration is described through tree history instead of the PR.** "The commit is no longer in the PR" → "the tree state is no longer in history" because the local host has no PR, and the text uses what the reviewer sees on screen. Both places that show this state use the wording: the picker row and the read-only banner. The host flag is the same `isLocalHost` used by the stale banner. Verdict terminology stays unchanged. Status: the host flag was superseded by the 2026-10-10 decision. It is now the host description's `iterations: 'tree'` field.
- **2026-09-23 · Only the active iteration's snapshot is "current" in the picker.** Once the PR moves beyond the latest snapshot, the menu row calls it "stale", as the indicator already did. Beside "active iteration · no route", "current" read as "up to date for the PR". Protocol status `current` still means "latest generation". The UI recalculates the label using the active iteration, with no server contract change.
- **2026-10-03 · Shift-clicking a picker row selects a slice between iterations, with no separate slice section.** The slice compares the iteration the tab currently shows with the row's iteration. Any pair is allowed, not only a pair ending at the active iteration, because the server already computed slices between any two. The older iteration is the base and the newer one is the head. A vanished iteration cannot be an endpoint. A URL with a base newer than its head is cleared. The current state's anchor is the current snapshot's iteration, not the active one. Shift-click starts from what is checked and visible on screen. While the current snapshot sits on a vanished iteration, Shift-click from the current state therefore acts as an ordinary click. Status: the anchor rule was superseded by the 2026-10-06 decision, with the reviewer selecting both endpoints. Arbitrary pairs, base/head ordering and the ban on vanished iterations remain in effect.
- **2026-10-06 · Slice selection takes two steps: Shift-click sets the first endpoint, and the next click on another iteration builds the slice.** The anchor "what the tab shows" was invisible. Shift-clicking the active iteration, which is usually the one being viewed, acted as an ordinary click, and the menu closed before the reviewer could choose the second one. The second click builds the slice even without Shift, so the hovered range preview matches either click. The first endpoint is local state in the menu and Overview card and does not enter the URL. Esc or clicking it again clears it.

## Server and storage

- **2026-09-09 · `SHERPA_LISTEN_HOST` can set the server's listening address.** The default remains `127.0.0.1`. The value `::` gives direct IPv6 access to a VM while preserving the CLI's local IPv4 connection. The UI link address is written to the manifest, so another `sherpa up` shows the same link. Token checks remain in place. Direct HTTP access is unencrypted, and changing the address requires a server restart. A second trade-off is accepted: behind an HTTP proxy, the SSE token in `?token=` ends up in its access logs. There is already no encryption, and the token lives no longer than the server.

- **2026-08-19 · The UI channel uses SSE, with a complete state snapshot on every change.** WebSocket is unnecessary (dependencies and manual reconnection), and granular events do not pay off because the queue is small. A tick every 30 s sends a fresh snapshot and also lazily expires leases when nobody calls the server. The UI↔server contract also lives in `@sherpa/protocol`, and the UI validates every snapshot with fail-closed behaviour.
- **2026-08-19 · Events take the token as a query parameter, while static assets need no token.** EventSource cannot set headers, so only the events endpoint accepts `?token=`, with the same constant-time comparison. Static assets contain no secrets. The token arrives in the URL fragment and never reaches the server. All `/api/*` endpoints require a token.
- **2026-08-21 · Heavy review data uses separate GET endpoints instead of the snapshot.** The diff and threads weigh megabytes and cannot enter every tick's snapshot. The event carries only a monotonic thread revision, and the UI rereads the endpoint. Error codes are `no_review_host` (404) and `host_unavailable` (502).
- **2026-08-27 · PR metadata moved into the snapshot, with no separate endpoint.** Metadata is small, breadcrumbs and headers across all views use one source, and updates after publishing a verdict arrive through events without a reread. Snapshot assembly is synchronous, so the server keeps a metadata cache populated outside assembly. Check status is nullable. An adapter that does not read it returns `null`, and the UI hides the row.
- **2026-08-20 · The server sweeps expired manifests for other PRs only on an actual start.** Walking the manifest directory was kept out of the thin CLI. The directory cleans itself on the next cold start.
- **2026-08-21 · IBM Plex fonts come from npm packages and are vendored by the build.** Files enter the bundle, with no runtime network access and no binaries committed to git. The workspace has `allowBuilds: false` because these packages' postinstall scripts are telemetry and must not run.
- **2026-11-01 · The npm package ships the IBM Plex license as `LICENSE-IBM-Plex.txt`.** The server module embeds the fonts, and the OFL requires its text to travel with them. Sans and Mono carry the same license file, so one copy covers both. A test fails if they diverge.
- **2026-08-21 · UI development pages, the state gallery and demo, stay out of the production bundle,** because otherwise fixtures would enter the server bundle. In development, `/api` is proxied to a running server using the manifest, with an ephemeral port.
- **2026-08-27 · The feedback channel requires neither a review host nor a running worker** *(the channel has multiple implementations, per the 2026-10-10 decision)*. The reader works without an agent, and feedback should too. The UI sends only what the server does not know (view, route phase and bundle version). The server adds the rest.
- **2026-09-02 · Per-PR UI state is a key-value table in the PR database, with one endpoint and whole-field replacement.** The contract schema defines the fields. Adding a field requires no migration, and a corrupt value falls back to the default for that field alone. Merging by key cannot represent the data because maps store explicit reviewer choices, and "restore the directory default" deletes a key. Writes are optimistic, delayed by ~300 ms. A closing tab flushes pending writes with a `keepalive` request. A failed initial read disables writes until reload. State stays in tab memory, and server-saved state remains intact. This removed the last `localStorage` use from the production UI.
- **2026-09-03 · New-version checks only notify.** The server compares the distribution's `version.json` with the published one and puts an update in the snapshot when the version is newer and has not been dismissed. "Later" lives in tab memory. A failed recheck neither erases a known version nor enters the cache, because one failure would otherwise hide the toast for half an hour. The failure reason stays out of the response and goes to server stderr because the UI has no reason to distinguish it. *(The failure-reason rule is superseded: a forced check from the palette returns `host_unavailable` with the reason, so the palette says "could not check" instead of "no updates".)*
- **2026-10-10 · The update channel, `UpdateChannel`, is a build parameter.** The core does not know where a new version comes from. The composition root passes a channel (`latest()`, `install()`, for example an npm registry) to `startServer`, while cache, TTL, dismissed version and comparison are shared in `UpdateChecker`. Without a channel, there is no check. The cache remembers the writing channel's `id` because the file is shared by all builds on the machine. The npm channel returns no command, and the toast branch without a command says "copy the directory again". Before connecting it, provide a command or separate the label *(the label was separated by the 2026-10-25 decision)*. The `startServer` parameter is optional while CLI server tests call it without a channel *(superseded by the 2026-10-10 feedback-channel decision: the parameter is required)*.
- **2026-10-10 · `uiUpdateInstall` contains the channel's command and link, without `kind`.** The installation type (distribution from a checkout or a copy) knew a specific distribution method and made the UI keep its README link. The channel now returns `dir`, `command` and `readmeUrl`, and the UI shows the command or directory with a link when available. *(The directory became optional in the 2026-10-25 decision.)*
- **2026-10-25 · A channel that does not know how the distribution was installed returns `dir: null`.** The npm channel knows neither the command nor the directory, and "copy the directory again" is wrong for an npm package. A toast without a command shows the directory only when present, along with an instruction link. *(The npm channel was removed by the 2026-11-01 decision.)*
- **2026-10-10 · The host's `disablesUpdateCheck` flag disables network update checks instead of its name.** The fixture plugin sets it. A development endpoint supplies the version there, and the channel supplies the update hint.
- **2026-10-28 · Without an update channel the UI does not offer an update check.** The snapshot carries `updateChannel`, whether the server is built with a channel, and without one the palette has no "Check for updates" command: there is nothing to check with, and "you have the latest version" would be untrue. A distribution updated by an external tool needs this. The flag describes the distribution, not the host: the fixture's `disablesUpdateCheck` turns off only the network request, and the command stays.
- **2026-11-01 · The npm distribution has no update channel.** Every new session runs `npx sherpa-review@latest`, so a toast saying "a new version is out" would only repeat what the next session does anyway. The composition root passes `updateChannel: null`, and `NpmUpdateChannel` is removed. The check core, toast and endpoints stay for a distribution with its own channel. The dev server uses `DEV_UPDATE_CHANNEL`, which knows no versions, so the dev endpoint still shows the toast to the gallery and e2e.
- **2026-10-10 · The feedback channel, `FeedbackChannel`, is a build parameter: `link` or `issues`.** The core does not know where feedback goes. With `link`, the Feedback button opens an external page without a form (for example, repository issues). With `issues`, there is a form, the channel implementation creates the issue, and its `discussionUrl` is the discussion link. Unavailability discovered only on submission (for example, a token could not be obtained) is an `unavailable` outcome from `create`, not an error. The form shows the same fallback as before. `feedbackChannel` and `updateChannel` in `startServer` are required. `null` means no channel (for feedback, `uiState.feedback: null` and no top-bar button). A root that omits a channel does not compile.
- **2026-09-04 · The update toast sits above the floating action panel.** On a wide PR, the panel reaches the left corner and would cover the toast buttons. The toast's Esc handling stays a local listener that works only with focus inside. It is not a layer in the shared stack, because a layer would dismiss the toast from anywhere.
- **2026-09-03 · Old iterations are not cleaned up, and no local event telemetry is collected.** After four stages, `~/.sherpa` uses 28 MB for 21 PRs, at most 3.1 MB per PR, so there is nothing to clean. Aggregated events from one user do not answer behavioural questions, and there is no event sink.

## Performance and tests

- **2026-08-19 · The CLI bundle is built once per test run, in global setup.** esbuild overwrites the file non-atomically, while test files run in parallel processes. Building in each one caused a race that could read a truncated bundle.
- **2026-08-25 · E2E is a separate Playwright package, outside the standard checks.** Browser tests are slow and can be flaky, so runs are explicit. There is one browser, chromium from the user cache, with no system installations. Each run gets a fresh temporary state directory (the reviewer's `~/.sherpa` is untouched) and the real built UI.
- **2026-08-25 · The frame-time budget on the large fixture is a mean ≤ 16.7 ms and p95 ≤ 33 ms** during programmatic scrolling in headless chromium. This gives twice the margin over the measured 2.3–5.4 ms so runs don't become flaky on a slow machine.
- **2026-09-03 · Performance is measured by intervals between frames, not just the cost of work within a frame.** On a route of 25 stops, the previous method reported 0.08 ms and looked perfect, even though the frame exceeded 16.7 ms. The 149 thousand DOM nodes cost the browser time, outside our code, and were absent from the measurement. The old series stays because it shows our share. The measurement covers 76 files out of 100 because cards collapsed for a reason do not request parsing.
- **2026-09-04 · Heavy routes shed work by unmounting a stop's diff column, rather than virtualizing individual lines.** The section, narrative, chips and viewed toggle always stay in the DOM. Beyond 2500px from the viewport, a placeholder of the measured height replaces the column, following the same contract as Full diff. `content-visibility: auto` was rolled back after measurement because it reduces neither the DOM nor the heap and worsens p95 on top of unmounting.
- **2026-09-24 · The performance spec runs in the standard e2e run, without a separate project or flag.** A minute and a half per run is acceptable, and checking the budget on every run catches regressions sooner.
